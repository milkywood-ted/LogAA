## 0. 원 문제의식 (재도입에서도 유효)

> "match rate가 높은 거지, 그게 문제라는 것과는 차이가 있다." — 사용자, 2026-07-21

Stage 4의 `score = Σ(weight×matched)/Σweight`는 **매칭 케이스의 패턴 시그니처가 로그에 재현된 비율**(일치도)이지 결함 확률이 아니다. 그런데 Stage 5는 `score ≥ definite_threshold`만으로 "판정: 문제"를 단언했다.

전제가 하나 있다: KB 패턴은 확정 분석에서 추출된 시그니처이므로 **패턴이 있으면 그 케이스와의 매치는 보장**된다(사용자 확인). 따라서 "정상 로그 오탐률" 같은 일반 이상탐지 프레임은 부적합하며, 진짜 간극은 "**케이스와 일치한다**"와 "**그 케이스가 결함이었다**"의 구분이다. 이 구분 정보는 케이스 스키마 v2(`cases.verdict` 등)에 이미 저장되고 있었고, 분석 경로가 읽지 않는 것이 문제였다.

이 문제의식과 아래 요구사항은 폐기 후에도 유효하다. 폐기된 것은 **구현**이다.

## 2. 폐기 판단

덧대는 수정(fallback 시 판정 비활성화 등)도 가능했으나, 결함이 판정 의미론의 뿌리(§4)에 있고 영향도·심각도가 커 **전면 rollback**을 택했다(사용자 지시, 2026-07-22). 모든 심각 결함이 "결함을 문제 아님으로 단언"하는 방향(false negative)으로 작동한다는 점이 결정적이다 — 이전 로직의 오류 모드는 "정상을 문제로 과잉 보고"(false positive)였고, 로그 분석 도구에서 전자가 훨씬 비싼 오류다.

### D1 — Winner suppression (심각)

winner/메인 케이스 선정은 **패턴 매칭 score로만** 이뤄진다 — MoE `_select_from_pool`의 `_sort_key`(현 `pipeline.py:674`)와 단일 모드 `_run_stage3_4`(현 `pipeline.py:1079`) 모두 `case_verdict` 미고려. 그런데 판정은 그 winner의 `case_verdict`로 결정됐다. 재현:

```text
winner  : 흔한-정상패턴 (score=0.9, case_verdict=no_defect) → 판정 "문제 아님"
minority: 실제-결함     (score=0.6, case_verdict=defect)    → 요약만 남고 버려짐
```

폐기 전에는 winner가 무엇이든 score 기준 "문제"였으므로 결함이 은폐되지 않았다. MoE ensemble은 교차 전문가 후보를 한 풀로 합치므로 no_defect가 defect를 이길 확률을 구조적으로 높인다. 정상 케이스의 description/analysis는 정상 로그와 잘 맞아 reranker 단계에서도 유리한 경향이 있어 악화 요인이 겹친다.

### D2 — Fallback mixing (심각)

Fallback(`_run_fallback`, 현 `pipeline.py:1111`)은 HIT 케이스의 자기 패턴 score가 낮으면 전체 패턴으로 재매칭해 `match_result`만 교체하고 `matched_case`는 원 케이스로 고정한다 — **의도된 설계 분리**(주석 명시)였다. PR #36이 판정을 `matched_case.case_verdict`로 도출하고 rationale/actions/scope를 프롬프트에 주입하면서 이 분리가 의미 오염이 됐다. 재현된 프롬프트:

```text
매칭 케이스 : 정상-전원재인가 (관련성 90%)          ← 케이스 X
- KERNEL-PANIC-시퀀스 (weight=1.0)                 ← 케이스 Y (전체 패턴 재매칭)
원 분석의 판정 근거: ... 결함 아님으로 종결          ← 케이스 X
## 판정: 문제 아님                                  ← 케이스 X의 case_verdict로 결정
```

커널 패닉 evidence 위에 다른 케이스의 "정상 종결" 근거를 붙여 "문제 아님"을 단언한다. `_prompt_no_defect`는 매칭 패턴을 "이미 무해한 것으로 확인된 현상"으로 서술하라고 지시하므로 최악의 문구가 조합된다. 더 나아가 fallback은 원래 "낮은 HIT를 구제해 더 강한 evidence로 '문제' 리포트를 만들기 위한" 장치인데, 이 결함과 결합하면 **더 강한 evidence를 능동적으로 찾아와서 '문제 아님'에 붙이는** 역전이 일어난다.

### D3 — Stage 6 안전망 무력화 (심각)

PR #36은 reflection 검증 기준 3을 다음과 같이 바꿨다 (diff 확증):

- 변경 전: "판정({verdict})이 진단 점수 및 매칭 결과와 **일관되는지 확인**하세요."
- 변경 후: "일치도가 높은데 판정이 '문제 아님'·'판정 불가'인 것은 **모순이 아니라 정상**입니다."

2축 의미론에서 문구 자체는 논리적이지만, 결과적으로 **D2가 만들어내는 정확한 증상(패닉 evidence + '문제 아님')을 잡을 유일한 자동 검증 단계에게 그것을 정상이라고 선언**했다. 결함과 그 결함의 탐지기 제거가 같은 PR에 동봉된 형태로, 결함 단독보다 질적으로 더 위험하다.

### D4 — first_hit 조기 중단 (심각, 조건부)

first_hit 모드의 중단 조건(현 `pipeline.py:959`)은 `matched` 비어있지 않음 — `case_verdict` 무관. 첫 전문가가 no_defect 케이스를 HIT하는 순간 **뒤 전문가들이 defect 케이스를 검색할 기회 자체가 사라진다**(D1은 "경쟁에서 밀림", D4는 "탐색 배제"). 폐기 전에는 조기 중단이 verdict에 무영향(어차피 score 기반)이라 무해한 최적화였으나, verdict 의미가 바뀌며 판정 왜곡 장치가 됐다. 현 config는 `ensemble`이라 잠재 상태지만 설정 한 줄로 활성화된다.

### D5 — pinned 경로 노출 (중간)

`_run_fallback`은 pinned를 구분하지 않는다. 사용자가 no_defect 케이스를 직접 지정(pinned, relevance 1.0)했는데 자기 패턴 score가 낮으면 전역 재매칭 evidence에 그 케이스의 no_defect가 적용된다 — "이 케이스로 분석해줘"라고 명시한 사용자에게 다른 케이스 증거로 "문제 아님"을 답하는 경로.

### D6 — minority 직렬화 공백 (중간)

`serialize_result`는 winner의 `matched_case`에만 `case_verdict`를 실었고 minority_reports에는 넣지 않았다(`ec46e8b` 확인). D1으로 묻힌 defect 케이스가 UI "기타 후보" 표에서도 결함 케이스인지 식별 불가 — 사람이 육안으로 복구할 마지막 채널까지 막힌 구조.

### D7~D9 (경미)

- **D7**: 프롬프트에 rationale/actions/scope 섹션이 추가됐지만 `_estimate_fixed_tokens`는 evidence+guidelines만 계산 → `num_ctx` 설정 시 truncation의 고정 토큰 과소평가. 실위험 낮음(198K).
- **D8**: `_CASE_VERDICT_TO_VERDICT.get(case_verdict, "문제")` — 사전 외 값이 조용히 "문제". DB CHECK(3값+NULL)로 완화되나 silent default 패턴.
- **D9**: `analyst`(실명)·`analysis_date`·`log_source`가 매 분석 history 행 `full`에 복제 — 개인정보 확산 + 케이스 수정 시 이력 스냅샷과 불일치 누적.

## 4. 공통 뿌리

9건을 관통하는 구조는 하나다: **`case_verdict`를 판정 근거로 승격시키면서, 그 판정이 서 있는 파이프라인 불변식을 검증하지 않았다.**

새 판정 로직이 암묵적으로 가정한 불변식 세 가지가 모두 기존 코드베이스의 (문서화까지 된) 동작과 충돌했다:

1. "`matched_case`와 `match_result`는 같은 케이스다" — fallback이 의도적으로 깨뜨림 (→ D2·D5)
2. "winner는 유일한 정답 후보다" — 다중 후보·MoE 풀·first_hit이 깨뜨림 (→ D1·D4·D6)
3. "어긋나면 Stage 6이 잡는다" — 같은 PR이 완화 (→ D3)

그리고 방향성: 모든 심각 결함이 false negative("결함을 놓치는") 방향으로 작동한다.

## 5. 프로세스 결함 (왜 못 잡았나)

1. **격리 단위 테스트만 존재** — `test_verdict_axes.py`는 `_determine_verdict`를 고립 검증(조합 전수)했으나, winner 선정·fallback·MoE와 엮인 통합 시나리오 0건. MoE 경로는 PR 이전부터 전용 테스트 부재.
2. **설계 문서의 검증 없는 안전 주장** — 설계서 §6.3은 "일치도 높음일 때만 원 분석 판정이 좌우"를 안전 논거로 제시했으나, "그 일치도가 어느 케이스의 패턴에서 왔는가"(fallback)와 "왜 그 케이스가 winner인가"(선정 기준)를 분석하지 않음.
3. **테스트 통과의 오독** — 108건 통과가 "회귀 없음"으로 읽혔으나, 기존 테스트가 못 보는 영역의 의미론 변경에는 무의미.

- [ ] **P2. 선정·판정 정합** — winner 선정에 case_verdict 반영(defect 우대) 또는 판정 단계에서 풀 전체 고려(no_defect 단언 보수화). first_hit 중단 조건에 동일 적용.
- [ ] **P3. Stage 6은 강화 방향으로만** — "evidence가 판정을 지지하는가"를 검증하게 하고, 모순 발견 시 레이블 변경이 아니라 경고 플래그를 출력에 추가. 검증 기준 완화 금지.
- [ ] **P4. 통합 테스트 선행** — ① defect+no_defect 혼재 다중 케이스 ② fallback 채택 ③ first_hit ④ pinned, 4개 시나리오의 verdict를 고정하는 테스트를 **기능 구현 전에** 작성 (D1~D5 회귀 방지).
- [ ] **P5. 직렬화 보완** — minority에도 case_verdict 포함(D6), 출처·담당 필드는 이력 복제 제외(D9), 미지 판정값은 silent default 대신 경고(D8), 토큰 추정에 신규 섹션 반영(D7).
