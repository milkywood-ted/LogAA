# 유사문제 판정 리포트 설계

작성일: 2026-07-23
상태: 설계 논의 중 (구현 미착수) — 뼈대 일부 확정, 세부는 계속 논의 필요
관련: `Document/케이스 판정 연계 재도입/PR36 요구사항 및 결함 리포트.md` (브랜치 `docs-pr36-defect-report`, main 미머지)

## 1. 배경 — 판정 라벨 리네이밍 (구현·머지 완료)

Stage 5 판정 3단계 라벨을 변경했다: "문제"→"유사문제", "알 수 없음"→"유사문제 없음", "불확실"은 유지.

- 이유: `_determine_verdict()`가 계산하는 score는 기존 KB 패턴/케이스와의 **유사도**이지 최종 결함 판정이 아닌데, 기존 라벨("문제")은 마치 최종 판정처럼 읽혔다. 이후 케이스 자신의 판정(`cases.verdict`: defect/no_defect/undetermined)을 리포트에 연결하는 작업(본 문서 대상)을 다시 진행할 때, "패턴이 잘 매칭됐다"와 "그 케이스가 실제로 결함이었다"는 서로 다른 축이라는 걸 이름에서부터 분리해두기 위함.
- 구현: PR #49 (커밋 `d79d2fe`, 머지 커밋 `b8a7c77`). `core/report_generator.py`(`_determine_verdict`·프롬프트 헤딩·문서 주석), `core/pipeline.py`, `core/reflection.py`, 프론트(`ResultPanel.jsx`/`HistoryPage.jsx`의 `VERDICT_ICON`/`VERDICT_CLASS` — 이력 데이터 호환을 위해 구버전 라벨 키도 함께 유지) 전체 반영, 테스트 100건 통과.

## 2. 판정별 라우팅 뼈대 (설계 확정, 구현 미착수)

score-tier 판정이 갈라지는 지점에서 세 갈래로 나뉜다.

| 판정 | 라우팅 |
|---|---|
| 유사문제 없음 | 신규 문제 분석 파이프라인 (완전히 새로운 분석 경로) |
| 불확실 | 사용자에게 3가지 선택지: 사용자 분석 입력 / 나중에 분석 입력 / 지금 신규 문제 분석 |
| 유사문제 | 매칭된 케이스의 `case_verdict` pass-through(score 크기와 무관, 문턱만 넘으면 이진 적용) |

- **신규 문제 분석 파이프라인**: 완전히 새로운 분석 경로. 현재 미구현이며 내부 설계는 아직 없음(오픈 아이템, §5 참고).

### 2-1. 파이프라인 실행 구조 — 분기 지점 (확정, 2026-07-25)

`_determine_verdict()`는 `match_result`(점수·매칭 패턴 유무)만 보는 순수 계산이라, **Stage 3/4 + Fallback 직후 이미 판정을 알 수 있다** — LLM을 부를 필요가 없다. 그런데 지금 코드는 이 계산이 Stage 5(`ReportGenerator.generate()`) 안에 파묻혀 있어, verdict 판정과 LLM 리포트 작성이 한 덩어리다. 이 때문에 지금은 "불확실"이든 "유사문제 없음"이든 **사용자가 아무것도 결정하기 전에 무조건 LLM이 리포트를 쓰고, 무조건 이력에 저장된다**(`Pipeline.run()`이 끝나며 `_finalize_run` → `_save_history`를 verdict와 무관하게 항상 호출).

이건 순서가 잘못된 것이다 — "불확실"은 사용자의 3택(§2-2)이 나와야 완결되는 것이고, "유사문제 없음"도 신규 파이프라인으로 가야 완결되는 것이라, 완결되기도 전에 저장·LLM 호출부터 해버리면(그리고 나중에 UPDATE로 덧대면) 미완결 상태를 완결된 것처럼 다루는 것이다.

**분기 지점**: Stage 3/4 + Fallback 직후, Stage 5 진입 전에 verdict를 먼저 계산한다(`_determine_verdict`를 `ReportGenerator` 밖에서도 호출 가능하도록 분리 — 로직 중복 없이 재사용).

- **유사문제**: 그대로 Stage 5 → Stage 6 → 저장까지 이어짐(변경 없음) — 이미 결과가 나온 경우이므로.
- **불확실**: 여기서 멈춘다. Stage 5(LLM 리포트 작성)·Stage 6(Reflection)·이력 저장을 전부 건너뛰고, `match_result`/`matched_case` 등만 담아 즉시 반환한다(report_md 없음). 3택 각각의 저장 시점은 §2-2 참고.
- **유사문제 없음**: "불확실"과 같은 지점에서 함께 멈춘다 — 원래 라우팅 표대로 신규 문제 분석 파이프라인으로 가야 하는 경로이기 때문이다. 신규 파이프라인이 아직 없다고 이 분기 자체를 안 만들면 안 된다(의존성이 낮은 "분기 지점"은 지금 만들고, 의존성이 높은 "신규 파이프라인의 실제 내용"만 나중으로 미룬다). **임시 목적지는 순수 placeholder다(확정, 2026-07-25)** — 지금 하던 자동 `_prompt_unknown` + `PatternGenerator` 호출은 유지하지 않는다. 이 자동 분석은 기존에도 제대로 동작하지 않고 있었으므로, 굳이 임시로 유지할 이유가 없다. 신규 파이프라인이 실제로 만들어지면 이 자리를 교체한다.

**job/이력의 관계 — "중단"이지 "일시정지"가 아니다(확정, 2026-07-25)**: 여기서 멈춘 job은 그냥 정상적으로 "done"이 된다 — "선택 대기 중" 같은 새 job 상태를 따로 만들지 않는다. verdict가 "불확실"/"유사문제 없음"인데 report_md가 없다는 사실 자체가 프론트에게 3택 UI를 보여줘야 한다는 신호다. 이후 사용자의 각 선택(즉시/나중에/신규 분석)은 **이 job을 이어서 재개하는 게 아니라 각각 독립된 새 요청이다** — job이 끝나며 이미 `serialize_result()`에 담겨 프론트로 전달된 `match_result`/`score`/`matched_patterns`/`warnings`만으로 충분하고, "즉시" 선택에서 LLM 지원(`_prompt_unknown`)이 필요하면 프론트가 들고 있는 원본 `log_paths`를 새 요청으로 다시 보내 Stage 1부터 재실행하면 된다(§7/§8에서 이미 이 방식이 가능하다고 확인됨). 즉 파이프라인 실행 상태를 어딘가에 살려뒀다가 이어붙이는 메커니즘 자체가 필요 없다.

**Stage 6은 사용자가 직접 쓴 내용에도 동일하게 적용한다(확정, 2026-07-25)** — LLM이 쓴 것이든 사용자가 쓴 것이든 검증 절차는 같다.

**PR5 재검토 필요**: 이미 구현했던 PR5(history 테이블에 별도 `user_content` 컬럼 + `PATCH` 엔드포인트, PR #55, 아직 미머지)는 "분석 내용은 같은 필드"라는 원칙을 어겼다 — `report_md`와 별개의 컬럼을 새로 만들었기 때문. 또한 이번 분기 지점 재설계로 저장 시점 자체가 바뀌므로(§2-2 참고), PR5는 이 문서의 최신 결론에 맞춰 다시 설계해야 한다.

### 2-2. 불확실 판정 시 3가지 선택지 (확정, 2026-07-24 — 저장 시점 2026-07-25 갱신)

1. **사용자 분석 입력(즉시)**: 사용자가 자신의 분석 결과를 직접 텍스트로 입력하는 별개 기능. LLM 관여는 자동이 아니라 **사용자의 선택에 따른 옵션**이며, 두 지점에서 관여할 수 있다:
   - 분석 지원: 기존 `_prompt_unknown`(LLM이 로그를 직접 분석하는 기존 경로)을 그대로 재사용할 수 있다. 단 이 함수의 내부 구현은 추후 갱신될 예정 — 지금은 그대로 유지한다.
   - 패턴 생성 지원: 기존 `PatternGenerator`가 관여할 수 있다.
   - **저장**: 사용자가 입력을 마칠 때까지 이력에 저장하지 않는다. 완료되면 그때 한 번에 완성된 내용으로 저장한다(INSERT 1회, UPDATE 불필요, §2-1).
2. **나중에 분석 입력**: 지금 결정하지 않고 미룬다. **이 선택 자체가 "지금은 완결 못 짓는다"는 결정이므로, 이 시점에 이력이 저장된다**(사용자 입력은 비운 채 INSERT, §2-1) — 이력 페이지에서 나중에 "사용자 분석 입력" 버튼이 노출되어 그때 완료할 수 있다(완료 시 그 row를 UPDATE). **이 경로는 사용자가 전적으로 스스로 분석하고 그 결과만 입력하는 것을 전제로 한다** — 1번의 LLM 지원(분석 지원/패턴 생성 지원)은 여기 해당하지 않는다, 순수 수동 입력만 가능하다. 사용자가 "나중에 분석 입력"을 선택하는 시점에 이 사실을 안내해야 한다(UI 요구사항).
3. **지금 신규 문제 분석**: 신규 문제 분석 파이프라인을 즉시 실행한다 — §2-1의 "유사문제 없음"과 같은 목적지(현재는 placeholder)로 수렴한다.

- "나중에 분석 입력"은 "사용자 분석 입력"으로만 이어진다 — "신규 문제 분석"에는 "나중에" 옵션이 없다.
- **UI 배치**: 분석 직후 리포트 판정이 "불확실"이면, 리포트 화면에 이 3가지 선택지 버튼을 노출한다. 이력 페이지의 "사용자 분석 입력" 버튼은 별도 구현이 아니라, 분석 직후 리포트의 "사용자 분석 입력"과 동일한 루틴을 그대로 탄다.

## 3. "유사문제" 내부 도달 경로 3가지 (코드 근거)

`_run_fallback`(`core/pipeline.py:1117-1184`)과 `_determine_verdict`(`core/report_generator.py`)를 근거로, "유사문제" 판정에 도달하는 경로는 아래 세 가지이며 `matched_case`의 유무가 다르다.

| # | 상황 | matched_case | fallback_original_score |
|---|---|---|---|
| ① | Stage 2 HIT, 케이스 고유 패턴 점수가 이미 threshold 이상 (fallback 미발동) | 있음 | None |
| ② | Stage 2 HIT였지만 고유 점수 낮아 fallback 발동 → 전역 재매칭 점수가 threshold 이상으로 채택 | None (§4 불변식, Option A로 비워짐) | 있음 |
| ③ | Stage 2가 애초에 MISS(케이스 자체를 못 찾음)인데 전역 패턴 매칭 점수가 threshold 이상 | None | None |

②③에서 matched_case가 None인 것은 패턴이 case_patterns 상 여러 케이스에 공유될 수 있어(n:n) 단일 케이스로 특정할 수 없기 때문이며, 이는 오류가 아니라 "같은 로그 패턴이 다른 시나리오에서도 재현될 수 있다"는 정상적인 경우를 반영한다.

②는 Stage 2에서 상황 유사 후보가 실제로 있었다(HIT — `relevance_score ≥ threshold`) — 상황 자체는 유사했다는 뜻이다. 다만 그 후보 케이스의 고유 패턴으로는 로그가 확인되지 않았는데, **상황은 같지만 원인이 다른 경우**로 보는 것을 대표 설명으로 삼는다. (그 외 논리적으로 가능한 소수 설명: 그 케이스의 패턴 정의가 좁아 로그 변형을 못 잡는 경우, 상황 매칭 자체가 false positive인 경우 — 둘 다 코드로 확인되지 않으며 부가적으로만 남긴다.) ③은 애초에 상황 유사 후보 자체가 없었던(MISS) 경우로, ②와는 "상황이 유사했는지"가 다르다.

## 4. 유사문제 리포트 내용 설계 (확정)

위 코드 레벨 3경로(①②③)와는 별도로, "실제로 매칭 근거(패턴)를 낸 케이스가 하나로 특정되는지" 기준으로 리포트 작성 방식을 두 갈래로 나눈다. ①은 상황·원인이 모두 일치해 특정된 경우, ②③은 상황 유사 여부와 무관하게(② 상황은 유사했으나 원인이 다름 / ③ 상황 유사 후보 자체가 없었음) 매칭 근거를 낸 케이스가 하나로 특정되지 않는 경우다.

### 4-1. 케이스가 특정되는 경우 (①) — 거의 같은 문제

매칭된 케이스를 그대로 참조한다 — 케이스명·관련성과 함께 그 케이스의 `verdict`를 pass-through 하고, `verdict_rationale`/`actions`/`notes` 등 기록된 정보도 함께 인용한다. 상황과 패턴이 둘 다 일치하므로 원인·해결책까지 확신할 수 있는 유일한 경우.

### 4-2. 케이스가 특정되지 않는 경우 (②③) — 패턴은 같지만 원인 케이스가 하나로 안 좁혀짐

패턴이 같다고 원인·해결책까지 같다고 확정할 근거는 없다(패턴만으로는 case_patterns n:n 관계상 여러 케이스가 걸릴 수 있음). 따라서 단일 케이스의 verdict를 pass-through 하지 않는다.

대신 이 패턴을 가진 기존 케이스들을 **참고 목록**으로 제시한다 — 각 사례의 상황·판정을 함께 노출하되, 지금 상황에 대한 최종 판정으로 특정 하나를 단정하지 않는다. 이는 "결정" 로직이 아니라 "정보 제시"이므로, 매칭 재귀속(과거 `_run_fallback` 수정 시 검토했다가 복잡도 문제로 폐기한 n:n 역조회 방식, Option B)에서 우려했던 판단 복잡도와는 성격이 다르다.

**목록 UI (확정, 2026-07-24)**: 목록 각 항목은 케이스명 + 상황을 한 줄 요약으로만 보여준다. 클릭하면 그 케이스의 상세 내용(판정·조치·근거 등 전부)을 볼 수 있다.

## 5. 미확정 / 후속 논의 필요 항목

**신규 문제 분석 파이프라인 관련 항목은 그 파이프라인 개발 착수 시점에 별도로 논의한다(2026-07-24 확정)** — 아래 항목들이 여기 해당하며, 지금은 더 진행하지 않는다.

- **신규 문제 분석 파이프라인 설계 ↔ `_prompt_unknown` 내부 갱신 (구상 단계)**: 이 두 항목은 서로 밀접하게 연관돼 있어 하나로 묶는다. 현재까지의 구상은 — 신규 문제 분석 파이프라인의 일부 단계를, 사용자가 `_prompt_unknown`을 통해 선택적으로 활용할 수 있게 하는 것. 즉 `_prompt_unknown`은 "사용자 분석 입력"에 쓰이는 독립적인 레거시 함수로 남는 게 아니라, 추후 갱신되면서 신규 파이프라인의 특정 단계(들)를 사용자가 수동으로 호출하는 진입점 역할을 하게 될 수 있다. 아직 "구상" 단계이며, 신규 파이프라인 자체의 단계 구성·`_prompt_unknown`이 정확히 어떤 단계를 어떻게 노출할지는 미정. **`_prompt_unknown`의 현재 구현은 이 갱신이 실제로 이뤄지기 전까지 그대로 유지한다** — §2-2의 "사용자 분석 입력"도 그때까지는 지금의 `_prompt_unknown`을 그대로 재사용한다.
- **"지금 신규 문제 분석"의 결과 저장 방식**: 목적지 자체는 §2-1/§2-2에서 정리됨 — "유사문제 없음"과 같은(현재는 placeholder인) 신규 파이프라인 분기로 수렴한다. 다만 신규 파이프라인이 실제로 만들어졌을 때, 그 실행 결과가 §2-1에서 미리 만든 pending 상태를 이어받아 채우는 건지 완전히 새 이력 레코드를 만드는 건지는 신규 파이프라인의 실행 방식(동기/비동기, job 구조 재사용 여부)이 정해져야 답할 수 있어 계속 미룬다.
