# 설계 검토 — 구현 실현 가능성

작성일: 2026-07-24
대상: `Document/분석 리포트 개선/유사문제 판정 리포트 설계.md`의 각 항목
성격: **구현 아님** — 실제 소스 검토를 통한 실현 가능성/충돌 여부 확인. 근거가 있는 것만 "확인됨"으로 적고, 근거를 찾지 못한 것은 그 사실을 그대로 적는다(추론으로 채우지 않는다).

---

## 1. §2 라우팅 뼈대 — score-tier 분기점

**확인됨**: `_determine_verdict()`와 `generate()`의 verdict 분기(`core/report_generator.py:121-149`)가 이미 if/elif/else 3갈래 구조로 되어 있다. 이 지점에서 라우팅을 갈라 붙이는 것 자체는 기존 구조를 깨지 않고 확장 가능하다 — 새 분기 로직을 위한 자리(hook point)가 이미 있다.

## 2. §4-1 "유사문제" → case_verdict pass-through — MatchedCase 필드

**확인됨**: `MatchedCase`(`core/kb_search.py:60-76`)에는 `verdict`/`verdict_rationale`/`actions`/`notes` 등의 필드가 없다. 이걸 채워 넣는 세 SELECT 호출부를 모두 확인했다:

- `load_case_by_name`(`kb_search.py:227`): `SELECT id, name, description, keywords FROM cases WHERE name = ?`
- `_vector_search`(`kb_search.py:383`): `SELECT id, name, description, keywords, analysis, chip_tags FROM cases ...`
- `_rerank`이 위 결과(`candidates`)를 그대로 사용해 `MatchedCase`를 생성(`kb_search.py:530-540`)

셋 다 판정 관련 컬럼을 조회하지 않는다. 반면 DB 컬럼 자체는 이미 존재한다(`core/db.py:239-253`, 케이스 스키마 v2 마이그레이션 — `verdict`/`verdict_rationale`/`actions`/`notes`/`symptom_module`/`defect_area_*`/`undetermined_reason*` 전부 있음).

**결론**: 컬럼은 있고 조회 경로만 없는 상태 — SELECT 확장 + `MatchedCase` 필드 추가로 해결되는 범위. 기존에 `chip_tags`/`references`를 이 방식대로 추가한 선례가 이미 있어(같은 파일, 같은 패턴), 구조적 충돌은 확인되지 않았다.

## 3. §4-2 "케이스 미특정" 참고 목록 — case_patterns 역조회

**확인됨**: 순방향(케이스 → 패턴)은 `_load_patterns`(kb_search.py)로 이미 있다. 역방향(패턴 → 케이스) 쿼리는 전혀 없는 게 아니라, 이미 한 곳에 존재한다 — `core/pipeline.py:824-830`:

```sql
SELECT DISTINCT case_id FROM case_patterns WHERE pattern_id IN (...)
```

단, 이건 MoE 프로파일 집계용(`_determine_target_profiles` 계열)이라 `case_id`만 뽑고 케이스 상세(이름/상황/판정)는 반환하지 않는다. 목록에 필요한 "패턴 id들 → 케이스 요약(이름/상황/판정) 목록"을 반환하는 함수는 없다 — 신규 작성이 필요하다.

**결론**: 신규 함수가 필요한 건 맞지만, 그 함수를 만드는 데 필요한 재료(역조회 SQL 패턴, 판정 컬럼 접근 방법)는 이미 코드베이스 다른 곳에 각각 존재한다. 참고로 과거 `_run_fallback` 버그 수정 때 이런 역조회 목적의 `load_case_by_id()`가 한 번 추가됐다가(Option B) 전체 되돌려져 지금은 없다 — 즉 "만들었다가 지운 적이 있다"는 선례이지, "만들 수 없다"는 근거는 아니다.

## 4. §4-2 UI — 목록 + 클릭 시 상세

**확인됨**: `frontend/src/components/CaseManagePage.jsx`에 동일한 패턴이 이미 있다 — `detailId` state로 선택된 항목을 추적하고, `{detailId && <CaseDetailModal caseId={detailId} onClose={...} .../>}` 형태로 조건부 렌더링(`CaseManagePage.jsx:1092`, `1256-1259`). 패턴용 `PatternDetailModal`도 동일 구조(`1709`, `1823-1825`).

**결론**: "목록 한 줄 + 클릭 시 상세 모달"은 이미 이 프로젝트에 있는 검증된 UI 패턴이다. 새로 고안할 필요 없이 그대로 재사용 가능 — 충돌 없음.

## 5. §2 "불확실" 3택 — 파이프라인 실행 구조

**확인됨**: `api/main.py`의 `/analyze`는 요청을 큐에 등록하고 `job_id`를 즉시 반환(202, `submit_job`), `/analyze/{job_id}/stream`이 SSE로 진행 상황을 스트리밍하다가 `done`/`error`로 끝난다(`api/main.py:59-100` 근방). 파이프라인(`Pipeline.run()`)은 한 번 시작되면 중간에 사용자 입력을 기다리는 지점 없이 끝까지 동기로 완주한다 — `_run_fallback` 등 내부 분기는 모두 자동 판단이고, 사용자 개입을 기다리는 대기 지점은 코드에서 확인되지 않았다.

**결론**: "불확실" 3택 버튼은 파이프라인 실행 도중 끼어드는 게 아니라, **이미 완료된 리포트에 대한 후속 액션**(새로운 별도 API 호출)으로 설계하면 기존 job 모델과 충돌이 없다. "지금 신규 문제 분석"을 누르면 새 job을 하나 더 제출하는 형태가 기존 구조와 맞다.

## 6. §2 "나중에 분석 입력" — history 갱신 (2026-07-24 갱신 — 전제 정정)

**확인됨**: `history` 테이블(`core/db.py:131-136`)과 그 라우터(`api/router/history.py`)를 전부 확인한 결과, **UPDATE 경로가 코드 어디에도 없다**. `core/pipeline.py`엔 INSERT만(`_save_history:1503`), `api/router/history.py`엔 `list_history`/`get_history`/`delete_history`/`clear_history`뿐이다.

대조군: 같은 프로젝트의 `jobs` 테이블(`api/job_store.py`)은 `update_job_running`/`update_job_done`/`update_job_error` 등 UPDATE가 이미 정상적으로 쓰이고 있다 — 즉 "이 코드베이스에서 행 업데이트가 기술적으로 어렵다"는 근거는 없고, 단지 `history` 테이블에는 아직 적용된 적이 없을 뿐이다.

**정정**: 처음엔 "대기 상태를 나타낼 컬럼/플래그"도 별도로 필요하다고 적었으나, 이는 "사용자가 입력한 분석 내용"을 다른 경로(LLM 자동 생성·신규 파이프라인 결과)의 분석 내용과 다른 종류로 구분해야 한다는 전제에서 나온 추측이었다. 실제로는 분석 내용이 누가(LLM/사용자/신규 파이프라인) 채우든 같은 하나의 필드로 취급된다(현재까지 확정, 추후 재검토 시 바뀔 수 있음). 이 전제라면 별도 상태/플래그 없이, **그 필드가 비어있는지 여부만으로 이력 페이지의 버튼 노출을 판단**할 수 있다.

**결론**: "나중에 분석 입력을 선택했다가 나중에 완료한다"는 흐름에 실제로 필요한 새 능력은 **`history` 테이블에 분석 내용 필드를 채워 넣는 UPDATE 경로 하나뿐**이다 — 이건 기존 패턴 확장이 아니라 이 테이블 기준으로는 신규 설계 대상이라는 결론은 그대로 유지되지만, 별도 상태 관리는 불필요하다.

## 7. §2/§5 "나중에 분석 입력" — 원본 로그 재접근 문제 (설계 결정으로 해소됨, 2026-07-24 갱신)

`serialize_result()`가 반환하는 `selected_logs`는 파일 **경로 키만** 저장하고 내용은 저장하지 않는다(`tests/test_serialize_result.py:38`의 주석 "경로 키만 (내용 아님)"으로 재확인). `_save_history` payload에도 로그 원문이나 Stage 1 정제 결과(`l_common`)는 들어가지 않는다. `/analyze` 요청 자체가 `log_paths`(서버 로컬 경로)를 받는 방식이라, 원본 로그 파일이 분석 이후에도 그 경로에 남아있는지는 코드로 확인할 수 없었다.

**갱신**: 이후 설계 문서(§2)에서 "나중에 분석 입력"은 사용자가 전적으로 스스로 분석하고 결과만 입력하는 순수 수동 경로로 확정됐다 — `_prompt_unknown` 등 LLM 지원은 "즉시" 입력에만 해당하고 "나중에" 경로엔 관여하지 않는다. "즉시" 입력은 분석 완료 직후 같은 요청 흐름 안에서 이뤄지므로 `l_common`이 이미 메모리에 있어 원본 로그 재접근이 애초에 필요 없다. 즉 이 항목이 실제로 걸리는 시나리오(나중에 + `_prompt_unknown` 재사용) 자체가 설계에서 빠지면서, 원본 로그 보존 여부를 확인해야 하는 근거 불충분 상태가 **더 이상 이 기능에는 해당하지 않게 됐다.**

## 8. §2 "사용자 분석 입력" — `_prompt_unknown`/`PatternGenerator` 재사용성

**확인됨 (PatternGenerator)**: `PatternGenerator.generate(text: str) -> GenerationResult`(`core/pattern_generator.py:65-76`)는 클래스 상태에 의존하지 않는 독립 공개 API로, 이미 `_try_kb_suggestion`(`report_generator.py:400-411`)에서 `problem_text` 하나만 넘겨 호출되고 있다. 사용자가 작성한 분석 텍스트를 그대로 이 함수에 넘기는 데 구조적 문제는 확인되지 않았다.

**확인됨 (`_prompt_unknown`)**: 모듈 레벨 순수 함수(`report_generator.py:597-625`)로 클래스 상태 의존이 없다. 다만 인자로 `l_common`(Stage 1 정제 로그)이 필요한데, 위 7번 항목과 동일하게 이게 history에 저장되지 않는다 — 분석 직후(같은 세션) 사용이면 문제 없지만, "나중에" 경로에서는 7번과 같은 제약을 그대로 받는다.

## 9. §5 신규 문제 분석 파이프라인 ↔ `_prompt_unknown` 갱신 (근거 없음, 명시)

이 항목은 신규 파이프라인 자체가 아직 설계·착수되지 않아 **비교/검증할 소스 코드가 존재하지 않는다.** "일부 단계를 `_prompt_unknown`에서 선택적으로 활용 가능하게 한다"는 구상이 실현 가능한지 여부는 신규 파이프라인의 단계 구성이 먼저 나와야 판단할 수 있고, 지금은 판단할 근거 자체가 없다. 확인 불가 상태임을 그대로 남긴다.
