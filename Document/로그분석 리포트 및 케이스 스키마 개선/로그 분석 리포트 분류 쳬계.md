# 로그 분석 리포트 분류 체계

판정(Verdict) · 조치(Action) 분류 기준 정의서

> 버전 2.0 | 갱신일: 2026-07-09

---

## 0. 분석 범위 및 설계 원칙

### 0.1 분석 범위

- 로그를 통한 분석의 범위는 **SW로 한정**하며, SW의 범주는 **Kernel Driver로 한정**한다.
- 단, **결함 판정의 범주는 SW로 한정되지 않는다.** 결함영역이 SW(Kernel Driver)인 경우 상세 분석을 기재하고, SW 외(HW / 환경 / 서드파티 / 검증계 등)인 경우 근거와 함께 그 판정 사실만 기재한다.

### 0.2 설계 원칙

- **판정(무엇이 확인되었나: 사실)과 조치(무엇을 할 것인가: 행동)의 두 축을 완전히 분리**한다. 사유는 판정이 담고, 조치의 하위에는 행동만 온다.
- 분류 정의문에는 특정 모듈에 대한 상대적 기준("나의 모듈이 아닌 곳" 등)을 두지 않는다. 위치는 모두 **절대 좌표(모듈명 등의 값)**로 기재하며, 이로써 조직·담당 변경과 무관하게 유연성을 유지한다.
- 각 건은 세 개의 위치 좌표로 기술된다:
  - **문제현상 발현 영역** — 어디서 보였나 (판정)
  - **결함영역** — 어디가 원인인가 (판정)
  - **수정 모듈 / 해결 주체** — 어디서 해결되나 (조치)
- 판정은 **단일 선택**, 조치는 **복수 선택 가능**하다.

## 1. 판정 (Verdict)

### 1.1 판정의 종류

결함 / 비결함 / 판정불가 — 단일 선택.

### 1.2 결함

분석 결과 문제가 확인된 경우. 아래 두 하위 필드를 **모두 필수**로 기재한다.

- **문제현상 발현 영역**: 현상이 관측된 모듈 (특정 모듈명)
- **결함영역**: 원인이 위치한 곳. 다음 중 하나의 값으로 기재한다.
  - **특정 모듈** (모듈명 기재)
  - **외부요인** — HW / 환경 / 서드파티 / 고객사 등, 제품의 올바른 동작에 관여하는 외부 구성 요소
  - **검증계** — 테스트 환경, 테스트 스크립트, 측정 장치 등, 동작을 관측·검증하는 장치. 제품의 올바른 동작 구현에는 관여하지 않는 영역

두 필드를 분리 기재함으로써 "현상은 특정 모듈에서 발현되지만 원인은 다른 곳에 있는" 케이스가 구조적으로 드러난다.

### 1.3 비결함

분석 결과 문제가 아닌 경우. 다음을 포함한다.

- 스펙(설계 의도)대로의 정상 동작
- 사용자 오해 또는 기대치 차이
- 조치가 불필요한 일회성 이벤트

### 1.4 판정불가

결론을 내릴 수 없는 경우. 하위 사유를 **단일 선택**으로 기재한다.

- **로그부족**: 로그 레벨·보존 기간 등의 문제로 근거가 부족한 경우
- **재현불가**: 재현이 되지 않아 결론을 내릴 수 없는 경우
- **기타**: 그 외 사유 (사유 서술 필수)

## 2. 조치 (Action)

조치의 구분 기준은 **수정 위치(어디서 해결되는가)**이다. 복수 선택 가능하며, 복합 케이스(예: 이관 + 방어적 수정)는 병기하여 기록한다.

### 2.1 수정 및 해결 (Fix and Resolve)

분석 대상 모듈(Kernel Driver)에 코드 변경이 발생하는 경우. **수정 모듈을 기재**하고, 하위 구분을 기재한다.

- **오류 수정 (Fix)**: 근본 원인을 수정하는 경우
- **방어적/회피 수정 (Defensive Change)**: 방어 로직·회피코드 등의 수정

결함영역과 수정 모듈이 다를 경우(원인이 있는 곳과 수정하는 곳이 다른 경우) 그 사실이 좌표 대비로 드러나며, 필요 시 별도 기재한다. 근본 수정과 방어/회피를 구분해 기록함으로써 기술 부채 추적이 가능하다.

### 2.2 추가 조치 (Additional Action)

판정을 내리기 위한 후속 분석 활동을 진행하는 경우. 주로 판정불가 건에 적용된다.

- 예: 추가 분석을 위한 로그 추가(Change SW by adding log), 재현 조건 확보, 재발 대기 후 재분석 등

### 2.3 유지 (Keep)

수정 위치 없음 — 추가 조치 없이 종결하는 경우.

- **비결함** 건 (예: 오발췌로 확인되어 종결)
- **결함이지만 수용·보류**하는 건 — 사유 명기 필수 (기술적 불가 / 우선순위·비용)
- **판정불가** 건 중 추가 조치 없이 종결하는 건

### 2.4 이관/외부 대응 (Handover)

해결이 조치 가능한 범주 밖에서 이루어지는 경우. **해결 주체를 명기**한다.

- 예: 타 모듈 수정, 고객사 수정, 서드파티 수정, HW 이슈에 대한 HW 조치, 검증계(테스트 환경·스크립트) 담당 조치 등

> **참고 — 열린 건 / 닫힌 건**: 2.1·2.2·2.4는 해결 활동이 계속되는 **열린 건**(수정 위치: 분석 대상 모듈 / 분석 중 / 그 외)이고, 2.3은 아무도 추가 조치를 하지 않는 **닫힌 건**이다. 이 구분이 리포트에서 건의 상태를 한눈에 드러낸다.

## 3. 좌표 조합 검증 — 대표 케이스별 기록 예시

세 좌표(발현 영역 / 결함영역 / 수정 모듈)와 판정·조치의 조합으로 모든 케이스가 곡해 없이 표현된다.

| 케이스 | 기록 방법 |
|---|---|
| 담당 모듈 문제, 수정 진행 | 결함(발현=A, 결함영역=A) + 수정및해결(Fix, 수정 모듈=A) |
| 다른 모듈의 문제 | 결함(결함영역=B) + 이관/외부 대응(대상=B) |
| 문제지만 수정 불가 | 결함(결함영역=A) + 유지(사유: 기술적 불가) |
| 현상은 담당 모듈, 원인은 타 모듈 | 결함(발현=A, 결함영역=B) + 이관/외부 대응(대상=B) |
| 타 모듈 원인 + 담당 모듈에 회피코드 | 결함(결함영역=B) + 이관/외부 대응(대상=B) + 수정및해결(방어적 수정, 수정 모듈=A) |
| 서드파티/고객사 원인 | 결함(결함영역=외부요인) + 이관/외부 대응(대상 명기) |
| HW 결함, HW 교체 요청 | 결함(결함영역=외부요인·HW) + 이관/외부 대응(HW 조치) |
| HW 결함, 일회성으로 종결 | 결함(결함영역=외부요인·HW) + 유지 |
| 테스트 스크립트 결함, 담당에 전달 | 결함(결함영역=검증계) + 이관/외부 대응(검증계 담당) |
| 테스트 환경 오발췌 | 비결함 + 유지 |
| 정상 동작 / 사용자 오해 | 비결함 + 유지 |
| 로그 부족으로 결론 불가 | 판정불가(로그부족) + 추가 조치(로그 추가) |
| 재현 안 되어 종결 | 판정불가(재현불가) + 유지 |

*(A = 분석자의 담당 모듈, B = 그 외 특정 모듈. 표기 편의상의 기호이며, 분류 정의는 좌표 값으로만 동작한다.)*

## 4. 운용 지침

- **도입 전 검증**: 최근 실제 분석 건 10~20개를 본 체계로 소급 분류하여, 어디에도 들어가지 않는 건이나 작성자마다 다르게 분류되는 건이 있는지 확인한다.
- **경계 기준 명문화**: 유지(수용·보류) vs 비결함의 경계(문제 여부를 스펙 문서 기준으로 볼지, 사용자 영향 기준으로 볼지)를 팀 내에서 합의하여 정의에 한 줄로 명기한다.
- **복수 선택 원칙**: 조치는 실태를 반영하도록 병기를 허용하며, 하나로 접지 않는다.
- **사유와 행동의 분리**: 조치 카테고리의 하위에 사유(원인의 성격)를 추가하지 않는다. 사유는 판정(결함영역)이 담는다. 이 원칙이 카테고리 목록의 재증식과 난잡화를 막는다.
