# 케이스 스키마 개선 — 구현 설계

> Implementation Spec v1.1 | 작성일: 2026-07-10 (v1.1: §7 확인 사항 3건 확정 반영) | 브랜치: `feat-case-format-improve`
> 근거 문서: `로그 분석 리포트 분류 쳬계.md`(v2.0) · `로그분석 리포트 작성 가이드.md`(v2.1) · `로그분석 리포트 템플릿.md`(v2.1) · `style/README.md`(UI 핸드오프)

---

## 0. 목표 및 범위

기존 케이스(name / description / analysis / keywords / profile_refs / chip_tags)에
분류 체계 v2.0의 **판정(Verdict) · 조치(Action) · 기본 정보** 필드를 추가하고,
케이스 관리 UI를 리포트 템플릿 v2.1 구조로 개편한다.

- 케이스 : 리포트 = **1:1**. 별도 테이블을 만들지 않고 `cases` 테이블을 확장한다.
- ChromaDB 임베딩(대상: description, analysis)과 메타데이터는 **변경하지 않는다**.
- 데이터 경로 4개 층을 순서대로 수정한다:
  `SQLite(core/db.py)` → `AA V2 API(api/router/cases.py)` → `backend 프록시(routers/cases.py)` → `frontend(api.js, CaseManagePage.jsx)`

### 확정된 설계 결정 (2026-07-10 논의)

| # | 항목 | 결정 |
| --- | --- | --- |
| 1 | 저장 방식 | **하이브리드** — 단일 선택·집계 축은 개별 컬럼(+CHECK), 조치는 `actions` JSON 컬럼 1개 |
| 2 | 임베딩 | 새 필드는 SQLite에만. ChromaDB 변경 없음 |
| 3 | 필드 매핑 | 이슈 번호/제목 → 기존 `case_references` 재활용(새 컬럼 없음). 분석자/담당 모듈 → 평문 컬럼(프로파일 FK 금지, UI prefill만). 분석 일자·로그 출처/기간 → 사용자 입력 가능, 필수 아님 |
| 4 | 판정불가 사유 | **단일 선택(라디오)** — 문서 v2.0이 규범. 프로토타입의 체크박스는 교정 |
| 5 | 필수 검증 | **AA V2 Pydantic에서 강제** — verdict는 모든 저장에서 필수, 조건부 필수 규칙은 §2.2 |

### 프로토타입(style/) 대비 교정 사항

구현은 style/ 핸드오프의 레이아웃·인터랙션을 따르되, 아래 2가지는 **분류 체계 문서를 우선**하여 교정한다.

| 항목 | 프로토타입 | 교정 후 |
| --- | --- | --- |
| 판정불가 사유 | 체크박스(복수) | **라디오(단일)** — 정의서 §1.4 "단일 선택" |
| 조치 선택 | 라디오(4개 중 1개만) | **체크박스(복수 선택)** — 정의서 §0.2 "조치는 복수 선택 가능", 병기 케이스(이관+방어적 수정) 지원 |
| 수정 항목의 유형 | 체크박스(둘 다 가능, 미지정 허용) | **라디오(오류 수정 / 방어적·회피 수정 중 하나)** — 가이드 §4 "중 선택" |

## 1. DB 스키마 (SQLite `cases` 테이블 확장)

`core/db.py`의 `_migrate()`에 `ALTER TABLE ADD COLUMN`으로 추가한다.
기존 행은 전부 기본값(NULL 또는 '')을 갖게 되며, **판정 미기재 = "작성 중" 케이스**로 간주한다.

### 1.1 추가 컬럼

```sql
-- 기본 정보 (섹션 01)
ALTER TABLE cases ADD COLUMN analyst        TEXT NOT NULL DEFAULT '';  -- 분석자
ALTER TABLE cases ADD COLUMN owner_module   TEXT NOT NULL DEFAULT '';  -- 담당 모듈 (UI에서 프로파일 값 prefill)
ALTER TABLE cases ADD COLUMN analysis_date  TEXT;                      -- 분석 일자 YYYY-MM-DD, 사용자 편집 가능
ALTER TABLE cases ADD COLUMN log_source     TEXT NOT NULL DEFAULT '';  -- 로그 출처 / 기간

-- 판정 (섹션 03) — 집계 축은 개별 컬럼
ALTER TABLE cases ADD COLUMN verdict TEXT
    CHECK(verdict IN ('defect','no_defect','undetermined'));
    -- 컬럼은 nullable (스키마 도입 전 레거시 행 때문). 단, API 저장 요청에서는 필수(§2.2)
    -- → NULL은 "스키마 도입 후 아직 수정된 적 없는 레거시 케이스"에서만 존재
ALTER TABLE cases ADD COLUMN symptom_module TEXT NOT NULL DEFAULT '';  -- 문제현상 발현 영역 (모듈명)
ALTER TABLE cases ADD COLUMN defect_area_type TEXT
    CHECK(defect_area_type IN ('module','external','verification'));   -- 결함영역 대분류
ALTER TABLE cases ADD COLUMN defect_area_module TEXT NOT NULL DEFAULT '';   -- type=module일 때 모듈명
ALTER TABLE cases ADD COLUMN defect_area_items  TEXT NOT NULL DEFAULT '[]'; -- type=external/verification일 때 하위 항목 JSON array
ALTER TABLE cases ADD COLUMN undetermined_reason TEXT
    CHECK(undetermined_reason IN ('insufficient_logs','not_reproducible','other'));
ALTER TABLE cases ADD COLUMN undetermined_reason_note TEXT NOT NULL DEFAULT ''; -- 사유='other'일 때 서술
ALTER TABLE cases ADD COLUMN verdict_rationale TEXT NOT NULL DEFAULT '';        -- 판정 근거

-- 조치 (섹션 04) — 복수 선택 + 반복 구조라 JSON 1개
ALTER TABLE cases ADD COLUMN actions TEXT NOT NULL DEFAULT '{}';

-- 특이사항 / 비고 (섹션 05)
ALTER TABLE cases ADD COLUMN notes TEXT NOT NULL DEFAULT '';
```

### 1.2 enum 값 ↔ 표시 문자열 매핑

DB에는 영문 토큰을 저장하고, 화면 표시는 프론트엔드가 변환한다.

| 컬럼 | 토큰 | 표시 |
| --- | --- | --- |
| verdict | `defect` / `no_defect` / `undetermined` | 결함 / 비결함 / 판정불가 |
| defect_area_type | `module` / `external` / `verification` | 특정 모듈 / 외부요인 / 검증계 |
| undetermined_reason | `insufficient_logs` / `not_reproducible` / `other` | 로그부족 / 재현불가 / 기타 |

`defect_area_items`(JSON array of strings)의 항목 토큰:

- external: `hw` / `env` / `third_party` / `customer` / `other:<서술>` — 표시: HW / 환경 / 서드파티 / 고객사 / 기타
- verification: `test_env` / `test_script` / `measurement` / `other:<서술>` — 표시: 테스트 환경 / 테스트 스크립트 / 측정 장치 / 기타

### 1.3 `actions` JSON 스키마

4개 조치는 **복수 선택 가능**. 선택된 조치의 키만 존재해도 되고, `selected: false`로 존재해도 된다(정규화는 Pydantic이 수행).

```jsonc
{
  "fix": {                        // 수정 및 해결 (Fix and Resolve)
    "selected": true,
    "entries": [                  // 반복 리스트 (style/ 핸드오프의 fixList)
      {
        "type": "fix",            // "fix"(오류 수정) | "defensive"(방어적·회피 수정) — 단일 선택
        "module": "모듈명",        // 수정 모듈 — 필수
        "change": "변경 내용 / 대상 버전"
      }
    ]
  },
  "additional": {                 // 추가 조치 (Additional Action)
    "selected": true,
    "items": ["add_logs", "secure_repro", "wait_recurrence", "other:<서술>"],
    "plan": "계획 자유 기술"
  },
  "keep": {                       // 유지 (Keep) — 닫힌 건
    "selected": true,
    "detail": "close_no_defect",  // "close_no_defect"(비결함 종결) | "accept_defect"(결함 수용·보류) | "close_undetermined"(판정불가 종결) — 단일 선택
    "reason": ""                  // detail="accept_defect"일 때 필수 (기술적 불가 / 우선순위·비용)
  },
  "handover": {                   // 이관/외부 대응 (Handover) — 해결 주체 명기
    "selected": true,
    "items": ["other_module", "customer", "third_party", "hw", "verification"],
    "owner": "해결 주체",          // 필수
    "channel": "티켓 / 전달 채널"
  }
}
```

`additional.items` 토큰 표시: 추가 로그 삽입 / 재현 조건 확보 / 재발 대기 / 기타.
`handover.items` 토큰 표시: 타 모듈 수정 / 고객사 수정 / 서드파티 수정 / HW 조치 / 검증계 담당 조치.

### 1.4 건 상태(열린 건/닫힌 건) 판별

별도 컬럼 없이 파생 규칙으로 계산한다 (정의서 §2 참고):

- **열린 건**: `fix` / `additional` / `handover` 중 하나라도 selected
- **닫힌 건**: `keep`만 selected
- **판정 미기재(레거시)**: verdict가 NULL — 스키마 도입 전 케이스에서만 발생. 다음 수정 시 판정 입력이 강제됨

프론트 목록 화면에서 상태 뱃지로 표시한다. (나중에 집계 축이 필요해지면 파생 컬럼으로 승격.)

## 2. AA V2 API (`AnalyzingAssistant_V2/api/router/cases.py`)

### 2.1 Pydantic 모델

```python
class FixEntry(BaseModel):
    type: Literal["fix", "defensive"]
    module: str                    # 필수 — 빈 문자열 거부
    change: str = ""

class FixAction(BaseModel):
    selected: bool = False
    entries: list[FixEntry] = []

class AdditionalAction(BaseModel):
    selected: bool = False
    items: list[str] = []          # add_logs / secure_repro / wait_recurrence / other:<...>
    plan: str = ""

class KeepAction(BaseModel):
    selected: bool = False
    detail: Literal["close_no_defect", "accept_defect", "close_undetermined"] | None = None
    reason: str = ""

class HandoverAction(BaseModel):
    selected: bool = False
    items: list[str] = []          # other_module / customer / third_party / hw / verification
    owner: str = ""
    channel: str = ""

class CaseActions(BaseModel):
    fix: FixAction = FixAction()
    additional: AdditionalAction = AdditionalAction()
    keep: KeepAction = KeepAction()
    handover: HandoverAction = HandoverAction()

class CaseSaveRequest(BaseModel):
    # ── 기존 필드 (유지) ──
    name: str
    description: str = ""          # = 2.1 보고된 현상
    keywords: list[str] = []
    analysis: str = ""             # = 2.2 분석 내용
    profile_refs: list[str] = []
    chip_tags: list[str] = []
    # ── 기본 정보 ──
    analyst: str = ""
    owner_module: str = ""
    analysis_date: str | None = None       # YYYY-MM-DD 형식 검증
    log_source: str = ""
    # ── 판정 ──
    verdict: Literal["defect", "no_defect", "undetermined"]   # 필수 — 기본값 없음
    symptom_module: str = ""
    defect_area_type: Literal["module", "external", "verification"] | None = None
    defect_area_module: str = ""
    defect_area_items: list[str] = []
    undetermined_reason: Literal["insufficient_logs", "not_reproducible", "other"] | None = None
    undetermined_reason_note: str = ""
    verdict_rationale: str = ""
    # ── 조치 / 비고 ──
    actions: CaseActions = CaseActions()
    notes: str = ""
```

### 2.2 조건부 필수 검증 (`model_validator`)

**verdict는 모든 저장 요청(생성·수정)에서 필수다.** 미포함 시 Pydantic이 422를 반환한다.
기존(레거시) 케이스도 수정하려면 판정을 입력해야 저장된다. 추가로 아래 조건부 규칙을 강제한다.

| 조건 | 강제 규칙 | 근거 |
| --- | --- | --- |
| (모든 저장) | `verdict` 필수 | 사용자 결정 (2026-07-10) |
| verdict = defect | `symptom_module` 필수, `defect_area_type` 필수 | 가이드 §3 "결함인 경우 필수" |
| defect_area_type = module | `defect_area_module` 필수 | 정의서 §1.2 "모듈명 기재" |
| defect_area_type = external/verification | `defect_area_items` 1개 이상 | 템플릿 §3 하위 항목 |
| verdict = undetermined | `undetermined_reason` 필수 | 가이드 §3 "판정불가인 경우 필수" |
| undetermined_reason = other | `undetermined_reason_note` 필수 | 정의서 §1.4 "사유 서술 필수" |
| actions.fix.selected | `entries` 1개 이상, 각 entry의 `module` 필수 | 가이드 §4 "수정 모듈 기재 필수" |
| actions.keep.selected | `detail` 필수 | 템플릿 §4 하위 단일 선택 |
| actions.keep.detail = accept_defect | `keep.reason` 필수 | 정의서 §2.3 "사유 명기 필수" |
| actions.handover.selected | `owner` 필수 | 가이드 §4 "해결 주체 기재 필수" |

판정과 조치 간 교차 검증(예: 비결함인데 fix 선택)은 **하지 않는다** — 문서가 금지하지 않는 조합을 막지 않는다.

### 2.3 CRUD 변경

- `INSERT` / `UPDATE` 문에 새 컬럼 추가. `actions`는 `json.dumps(req.actions.model_dump(), ensure_ascii=False)`로 직렬화.
- `_row_to_case_summary()`: 새 필드 전부 포함. `actions` / `defect_area_items`는 JSON 파싱해서 반환.
- **목록 응답**(`GET /cases`)에도 `verdict`와 건 상태 계산에 필요한 최소 필드(`actions`의 selected 플래그)를 포함한다 — 목록 뱃지용.
- ChromaDB 호출(`_kb.add_case(...)`)은 **변경 없음** (기존 인자 그대로).

## 3. backend 프록시 (`backend/routers/cases.py`)

- `CaseSaveRequest`와 하위 모델(§2.1)을 **동일하게 미러링**한다.
  (프록시 Pydantic에 없는 필드는 `model_dump()`에서 조용히 탈락하므로 누락 금지.)
- 조건부 필수 검증은 AA V2에만 두고, 프록시는 형태 검증만 한다 (검증 로직 이중화 방지).
- 엔드포인트 추가/삭제 없음.

## 4. frontend (`api.js`, `CaseManagePage.jsx`)

### 4.1 api.js

- 요청/응답이 새 필드를 그대로 담아 보내므로 함수 시그니처 변경 없음 (body에 필드 추가만).

### 4.2 CaseForm — 템플릿 v2.1 구조로 개편

style/ 핸드오프의 레이아웃(번호 섹션 카드, 확장형 카드, fixList)을 따르되,
색·폰트는 **기존 `pm-*` 클래스와 CSS 변수 테마**에 맞춘다 (핸드오프의 하드코딩 hex를 그대로 쓰지 않음).

```text
01 기본 정보     케이스 이름* / 분석자 / 담당 모듈(프로파일 prefill) / 분석 일자(date input, 기본값 오늘, 편집 가능) / 로그 출처·기간
                 └ 외부 참조 ID(기존 ReferencesSection을 이 섹션으로 이동 — 이슈 번호/제목 역할)
02 현상 및 분석  보고된 현상(기존 description) / 분석 내용(기존 analysis)
03 판정          판정(라디오 3, 필수*) / 발현 영역(텍스트) / 결함영역(확장형 카드 3, 라디오)
                 / 판정불가 사유(라디오 3 + 기타 텍스트) ← 프로토타입 체크박스 교정
                 / 판정 근거(textarea)
04 조치          확장형 카드 4 — 체크박스(복수 선택) ← 프로토타입 라디오 교정
                 ├ 수정및해결: fixList(추가/삭제, 항목별 유형 라디오 + 모듈 + 변경 내용)
                 ├ 추가 조치: 체크박스 + 기타 + 계획
                 ├ 유지: 하위 라디오 3 + 수용·보류 사유
                 └ 이관/외부 대응: 체크박스 + 해결 주체 + 티켓/채널
05 특이사항/비고 textarea (notes)
── 시스템 필드 ── 키워드 / Chip Tags / Profile Refs / 연결 패턴 (기존 그대로, 별도 섹션으로 유지)
```

- 판정/결함영역/조치 카드의 상세 패널은 **조건부 렌더**(선택 해제 시 언마운트)로 구현해 stale 상태를 방지한다 (핸드오프 지침).
- 프론트 검증: §2.2와 같은 규칙을 저장 버튼 시점에 검사해 인라인 안내를 띄운다.
  최종 방어선은 AA V2(422 응답)이며, 422 detail 메시지를 폼 상단에 표시한다.

### 4.3 CaseDetailModal (읽기 모드)

- 판정 요약 뱃지: 결함(빨강 계열) / 비결함(초록 계열) / 판정불가(회색) / 판정 미기재(레거시 — 회색 점선 등 구분 표시).
- 세 좌표(발현 영역 / 결함영역 / 수정 모듈·해결 주체)를 한 줄 요약으로 표시 — 정의서의 "좌표 대비" 가시화.
- 조치별 상세(fixList 표, 이관 대상 등)와 열린 건/닫힌 건 상태 표시.

### 4.4 케이스 목록 (CasesTab)

- 각 행에 판정 뱃지 + 열린/닫힌/미기재 상태 표시.
- (선택) 판정별 필터 드롭다운 — 기존 프로파일 필터 옆. 본 단계에서는 뱃지만 필수, 필터는 여유 시.

## 5. 마이그레이션 / 호환성

- 기존 케이스: 새 컬럼이 전부 기본값 → 목록/상세에서 **"판정 미기재(레거시)"**로 표시. 데이터 백필 없음.
- 레거시 케이스는 **로드해서 수정하는 시점에 판정 입력이 강제**된다 (verdict 없는 저장 요청은 422). 점진적으로 판정이 채워지는 구조.
- 기존 API 소비자(분석 파이프라인 등)는 description/analysis/keywords만 사용하므로 영향 없음.
- `AnalyzingAssistant`(V1)은 수정하지 않는다 — 대상은 V2만.

## 7. 확정 이력

v1.0의 확인 필요 사항 3건은 2026-07-10 사용자 결정으로 모두 확정되어 본문(v1.1)에 반영됨:

1. **verdict 필수** — 모든 저장 요청에서 필수(§2.2). 레거시 케이스는 로드 후 판정을 추가 입력하여 저장. "작성 중 초안" 개념은 채택하지 않음.
2. **조치 복수 선택** — 정의서 원칙대로 체크박스(복수 선택)로 교정(§0). 프로토타입의 라디오는 오류. UI 조정은 추후 가능하나 현 단계는 정의서를 따름.
3. **수정 항목 유형 단일 선택** — fixList 각 항목의 유형(오류 수정/방어적·회피 수정)은 라디오 단일 선택(§0, §1.3). 두 유형이 모두 필요하면 항목을 2개 등록.
