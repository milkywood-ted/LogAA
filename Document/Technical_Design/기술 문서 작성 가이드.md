# 기술 문서 작성 가이드

LogAA 프로젝트에서 기술 설계 문서를 작성할 때 따르는 절차와 표준 목차를 정의한다.

- 근거 규칙: `expert-claude/instruction_and_rule/basic_rule.md`(결정 정책), `verification_instruction.md`(Examinator 검증), `git_commit_rule.md`(커밋 정책)
- 전례: `Document/로그분석 리포트 및 케이스 스키마 개선/케이스 스키마 개선 구현 설계.md`, `expert-claude/document/architect_korean.md`(Architect 프로필 출력 형식)

## 1. 진행 프로세스

### 0단계 — 범위 확정 (사용자 입력 필요)

문서의 주제, 독자, 저장 위치를 확정한다. 이 단계가 끝나야 이후 단계의 깊이가 정해진다.

확정 체크리스트:

- [ ] **주제** — 어떤 기능/시스템에 대한 설계 문서인가?
- [ ] **저장 위치** — `Document/<주제>/` 하위 (기존 관례)
- [ ] **진행 방식** — 직접 수행 또는 expert-claude 서브에이전트(Analyst → Architect → Examinator) 파이프라인. 단일 주제의 결합된 설계 추론이라면 직접 수행을 권장.

### 1단계 — 요구사항·제약 정리 (Analyst 역할)

설계 문제를 정확히 기술하고, 충족해야 할 요구사항 / 판단 기준 / 제약 / 위험을 추출한다. 각 항목에 근거와 확신도(high/medium/low)를 붙인다 (basic_rule의 output_quality 준수).

### 2단계 — 기존 구조 탐색

설계 결정이 기존 코드·문서에 의존하는 부분만 선별적으로 탐색한다 (backend, AnalyzingAssistant_v2, frontend 등 관련 지점). 전면 탐색이 아니라 결정에 필요한 공백만 채운다.

### 3단계 — 설계 결정 도출

컴포넌트·인터페이스·데이터 흐름·기술 선택을 결정하되, basic_rule의 decision_policy를 따른다:

- 고임팩트이면서 (되돌리기 어렵거나 우세안이 없는) 결정 → **문서 작성 전에 사용자에게 에스컬레이션** (대안 + 트레이드오프 + 권고안 제시)
- 저임팩트·가역적 결정 → 가정으로 명시하고 진행 (ASSUME-AND-LOG)

"확정된 설계 결정 → 문서화" 순서로 진행한다 (케이스 스키마 개선 작업 전례와 동일).

### 4단계 — 문서 작성 및 검증

확정된 결정을 문서로 작성한 뒤, Examinator 관점의 독립 검증(요구사항 커버리지 각 항목이 근거와 함께 충족되는지 pass/fail 점검)을 거쳐 미충족 항목은 반복 수정한다 (verification_instruction 준수).

### 5단계 — 사용자 리뷰 → 확정 → 커밋

사용자 리뷰 후 확정 이력을 문서에 남기고, `docs:` 타입으로 커밋한다 (git_commit_rule: 작업 단위 즉시 커밋).

## 2. 표준 목차

이전 구현 설계 문서와 Architect 프로필의 출력 형식을 결합한 구조이다:

1. **목표 및 범위** — 해결하려는 문제, 범위 안/밖, 확정된 결정 요약
2. **요구사항·제약** — 1단계 산출물 참조
3. **아키텍처 개요** — 선택한 접근법과 근거 한 단락
4. **컴포넌트 설계** — 각 컴포넌트의 책임·경계·수정 지점 (파일 경로 명시)
5. **인터페이스/계약** — API·데이터 스키마·핵심 시그니처
6. **데이터·제어 흐름** — 요청이 시스템을 통과하는 경로
7. **트레이드오프 & 대안** — 검토한 옵션과 선택 이유
8. **마이그레이션/호환성** — 해당 시
9. **구현 단계** — Phase 분할 + 단계별 사용자 확인 체크리스트
10. **확정 이력 & 미해결 질문**

## 3. 작성 원칙

- 실질 내용이 없는 섹션은 채우지 않고 생략한다 (boilerplate 금지).
- 모든 결정은 그것을 추동한 요구사항/제약을 참조하며 정당화한다 — 대안이 없었던 듯 제시하지 않는다.
- 수정 지점은 파일 경로로 명시하여 다운스트림(구현·검증)에서 추적 가능하게 한다.
- 요구사항을 충족할 수 없거나 두 요구사항이 충돌하면 명시적으로 기술한다.
