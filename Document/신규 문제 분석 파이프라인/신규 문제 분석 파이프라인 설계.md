# 신규 문제 분석 파이프라인 설계

작성일: 2026-07-26
상태: 개념 설계 진행 중 (아키텍처 개요까지 확정, 컴포넌트/인터페이스 설계 전 단계)
관련: 저장소 루트 `analysis_upgrade`(2026-05-14 원 설계 노트) — 이 파이프라인이 완성하는 "유사이력 없는 신규 문제" 경로의 최초 구상. `Document/Technical_Design/AnalyzingAssistant_v2 기술 설계서.md` — 이 문서가 참조(수정 없이)하는 기존 파이프라인.

## 1. 목표 및 범위

### 배경

- 현재 `AnalyzingAssistant_v2`는 "유사 케이스 있음"(KB 벡터검색+패턴매칭) 경로만 구현돼 있다. 유사 이력이 아예 없는 "신규 문제"를 위한 경로는 없다 — 저장소 루트 `analysis_upgrade` 노트(현 파이프라인 이전 원 설계)에 이미 "신규 문제로 판정된 경우 ... 순수하게 사전지식만을 바탕으로 분석하는 영역 ... FRC driver source code 전체를 지식 베이스에 넣는다"는 구상이 있었으나 미구현으로 남아 있었다.
- 사내에 `/Users/tedkim/프로젝트/DTV_soc_driver`라는, Samsung DTV SoC 커널 드라이버(`sdp_frc`, `sdp_drm-dp` 등)를 칩별(rheal/pontusm/oscarp/rheam)로 심층 분석한 소스코드 분석자료가 별도 저장소로 존재하며, 이를 신규 문제 분석의 배경지식으로 활용할 수 있음을 확인했다.

### 목표

신규(미지의) 문제는 유사 이력(케이스)이 없다는 전제 위에서, **단일 확정 진단이 아니라 "분석에 도움이 되는 유용한 참고자료"를 산출**하는 것이 목표다. 하나의 결론으로 단정짓기엔 부정확 위험과 그에 따른 리스크가 크고, 디버깅은 LLM이 갖지 못한 경험·통찰이 크게 관여하는 영역이기 때문에, 여러 "분석 전문가(=분석 프로파일)"가 각자 독립적으로 분석한 결과를 사용자에게 나열해 제시하고 최종 판단은 사람이 내리게 한다.

### 범위 안

- 사용자가 지정한 1개 이상의 분석 프로파일(전문가) 각각에 대해: 프로파일별 로그 정제 → DTV_soc_driver 참고자료 기반 분석 → 결과 산출
- 여러 전문가의 산출물을 동등하게(승자 선정 없이) 사용자에게 제시

### 범위 밖 (현재 단계)

- **"적용 가능한 전문가"의 자동 판단.** 어떤 전문가가 이 문제에 관련 있는지 아는 것 자체가 분석적 통찰이므로, 자동 선정 로직을 두지 않고 전적으로 사용자 지정에 의존한다.
- **분석 결과의 case 편입.** 최종적으로는 염두에 두고 있으나(§10 확정 이력 참고), 신규 분석 자체의 품질 확보가 선행 과제이고 편입 자체는 난이도가 낮고 의존성도 단순한 별도 작업이라 지금 범위에 넣지 않는다.

## 2. 요구사항·제약

- **[제약, high] 기존 소스 수정 금지.** 신규 파이프라인은 기존 LogAA 소스코드(`AnalyzingAssistant_v2`/`backend`/`frontend`/`puller`)를 절대 수정하지 않고 새로 구축한다. 기존 코드·DTV_soc_driver 자료를 **참조**하는 것은 허용, **수정**은 금지. (사용자 명시)
- **[제약, high] 코드 위치.** LogAA 저장소 내 새 최상위 디렉토리에 구축한다(완전 별도 repo 아님 — 같은 git 히스토리·작업 디렉토리라 기존 코드·DTV_soc_driver 자료 참조가 쉽고, `Document/`·`deploy/` 체계를 재사용할 수 있어서). 디렉토리 이름은 미정.
- **[요구사항, high] 전문가 정체성 재사용.** "분석 전문가"는 새로 만드는 개념이 아니라 `AnalyzingAssistant_v2/core/profile.py`의 기존 `Profile`(`analysis_guidelines`/`prefilter_keywords`/`knowledge_refs`/`category`) 개념을 그대로 쓴다. 실사용(사내) 환경에 `DTV_FRC`, `DTV_DP` 프로파일이 이미 존재한다(로컬 dev repo의 `config/profiles/`는 비어 있음).
- **[요구사항, high] 전문가 선정은 100% 사용자 지정.** 시스템이 "적용 가능한 전문가"를 자동 판단하지 않는다 — 사용자가 1개 이상 프로파일을 직접 지정한다. 이에 따라 지정된 전문가들은 서로 조율·순서 없이 완전 독립 병렬로 실행된다.
- **[요구사항, medium] 칩 기반 자료 축소.** defect에는 이미 칩 정보가 주어지며, 이를 이용해 프로파일이 참조하는 DTV_soc_driver 자료를 칩 단위로 좁힌다 — 기존 `merge_profiles(..., chip=...)`가 `knowledge_refs`를 칩으로 필터링하는 것과 같은 축이다.
- **[제약, medium] DTV_soc_driver 자료의 성격.** 이 자료는 사례(case) 데이터가 아니라 소스 코드 분석 참고자료(reference)다. 실제 발생한 특정 문제를 가리키지 않으므로 `cases`/`patterns` 스키마로 직접 변환·임포트하지 않는다 — 전문가별 분석 단계(Stage 2)에서 배경지식으로만 주입한다.
- **[제약, medium] 프로파일 ↔ DTV_soc_driver 자료 매핑은 이름으로 자동 추론 불가.** `DTV_FRC` → `analysis/sdp_frc/<chip>/`, `DTV_DP` → `analysis/sdp_drm-dp/<chip>/`(대상 모듈 `tztv-media-sec/sdp_drm`, device flag `dp`) — 프로파일 이름과 폴더 이름이 문자열 1:1 변환이 아니므로(`DTV_DP`→`sdp_drm-dp`) 명시적 매핑 설정이 필요하다(§10 미해결 질문).

## 3. 아키텍처 개요

유사 이력 매칭(기존 Stage 2 KB search)이 필요 없다는 전제 위에서, 기존 `AnalyzingAssistant_v2`(6-Stage)보다 훨씬 단순한 3단계 파이프라인으로 설계한다.

```
[입력] problem_text, raw_logs, chip, 사용자가 지정한 전문가(프로파일) 목록 (1개 이상)
         │
         ▼  (지정된 전문가 수만큼 완전 독립 병렬 실행 — 조율/순서 없음)
┌─────────────────────────────────────────────┐
│ Stage 1 — 전문가별 로그 정제                    │
│   그 프로파일의 prefilter_keywords로 필터링      │
│                                               │
│ Stage 2 — 전문가별 분석                        │
│   입력: 정제된 로그 + problem_text              │
│        + analysis_guidelines                  │
│        + DTV_soc_driver 참고자료(프로파일→      │
│          서브시스템 매핑, chip으로 좁힌 문서)      │
│   출력: 가설 + 근거 + 사실/추론/가정 구분         │
│        + 불확실성 표기                          │
└─────────────────────────────────────────────┘
         │
         ▼
Stage 3 — 전문가별 산출물을 사용자에게 나열 제시 (승자 선정 없음)
```

기존 `AnalyzingAssistant_v2`의 MoE 앙상블(`pipeline.py`의 `moe_traversal_mode`, 전문가별 Stage1 정제 `moe_per_expert_stage1`)이 "여러 전문가 병렬 실행" 골격의 선례이긴 하나, 그 구조의 "winner 수렴 + minority 축소"는 이 파이프라인의 목적(다중 관점 동등 제시)과 반대이므로 그대로 채택하지 않는다.

## 4. 컴포넌트 설계

### Stage 1 — 전문가별 로그 정제

**구현 방식(확정, 2026-07-26)**: 기존 `AnalyzingAssistant_v2/core/log_refiner.py`(`LogRefiner`/`RefineConfig`)를 import·의존하지 않고 **완전히 새로 구현**한다 — 목적이 다르기 때문(기존은 "케이스 매칭 전제의 공통 1회 정제"이고, 이쪽은 "전문가별 독립 정제"). 다만 그 코드의 접근 방식(포맷 파서 분리, fingerprint 기반 collapse 등)은 설계 아이디어 차원에서 참고할 수 있다.

**필요 기능(확정)**:

- **포맷 파싱** — 로그 라인에서 타임스탬프·메시지를 분리한다. DTV_soc_driver `golden_capture/CAPTURE_SPEC.md`의 dmesg/debugfs `inlog`는 캡처 경로(콘솔 vs 링버퍼)와 레벨 게이팅 깊이만 다를 뿐 **라인 포맷은 동일**(`[타임스탬프][S_F] 메시지`)하므로 범용 파서 하나로 충분 — 소스별 분기 불필요(2026-07-26 정정). `mirror_log`(레지스터 접근 이력 테이블, printk 텍스트와 구조가 다름)는 `raw_logs` 입력 범위에 포함하지 않기로 확정(2026-07-27) — 파서가 다룰 필요 없음.
- **반복/버스트 collapse** — 동일 로그가 짧은 시간에 폭주할 때 압축.
- **키워드 필터** — 프로파일의 `prefilter_keywords` 기반 OR 매칭.

**부가 옵션(핵심 요구사항 아님, 필요해지면 후순위로 추가)**:

- 앵커 기반 시간 윈도우 추출.

### Stage 2 — 전문가별 분석

**DTV_soc_driver 자료 검색 방식(확정, 2026-07-27)**: 임베딩 의미검색 없이, **로그인덱스 정확매칭 + 번호슬롯 규칙 기반 문서선택**의 결정론적 2단계로 처리한다.

1. **로그 앵커 매칭** — Stage 1에서 정제된 로그 라인을 `<module_root>/<chip>/11_log_index.tsv`의 `match_key` 컬럼에 대조한다(포맷 문자열의 변수부를 제거하고 리터럴로 매칭 — `analysis/sdp_frc/README.md` §4-7 방식 그대로). 매칭되면 `file:line` + `subsystem` 태그를 얻는다.
2. **문서 선택** — 00~12 번호 슬롯은 서브시스템 공통 관례임을 확인했다(00=계획, 01=아키텍처, 02=init/probe, 03=ioctl, 04=irq, 05=power, 06=command/pipeline path, 07=debug, 08=external contract, 09=framework 통합, 10=결함매트릭스, 11=로그인덱스, 12=이벤트시퀀스 — `sdp_frc`·`sdp_drm-dp` 양쪽에서 슬롯 번호가 동일함을 diff로 확인, 09만 서브시스템별 제목이 다름). 1번의 `subsystem` 태그에 대응하는 02~09 문서를 선택하고, 10(결함매트릭스)·12(이벤트시퀀스)는 항상 기본 포함한다. 각 문서가 수십~수백 줄로 짧아 문서 전체를 통짜로 주입하며, 문서 내부를 추가로 쪼개지 않는다.

**임베딩 의미검색은 현재 도입하지 않음(확정 사유)**: 의미검색이 실제로 푸는 문제("자연어 질의로 어느 서브시스템/문서를 볼지 찾기")가 이 설계엔 없다 — 사용자가 전문가(프로파일)를 지정하는 순간 서브시스템이 이미 확정되기 때문. 로그→코드 매칭은 포맷 변수만 다른 정확매칭 문제라 의미검색보다 리터럴 매칭이 더 적합하다. 이 결정론적 레이어와 임베딩 레이어는 배타적이지 않고 덧붙이는 관계이므로(로그가 log_index 커버리지 밖이거나, 서브시스템 증가로 문서가 통짜 주입 못 할 만큼 커지는 시점에), 필요해지면 기존 로직을 갈아엎지 않고 나중에 얹을 수 있다.

**소비 제외 대상**: `_fact_extract.txt`/`_func_inventory.txt`(생산 중간 산출물, `analysis/tools/README.md` 참고) — 파이프라인이 읽지 않는다.

#### Stage 2 LLM 호출 구조 (확정, 2026-07-27)

**공통 질문이 성립하는 근거**: 신규 문제는 유형이 사전에 파악되지 않으므로 "문제 유형별 질문 세트"를 만들 수 없다. 그런데도 공통 질문이 성립하는 이유는 문제들이 서로 비슷해서가 아니라 **참고자료의 모양이 고정돼 있어서**다 — 00~12 번호 슬롯이 각각 답할 수 있는 질문 종류가 정해져 있으므로, 문제가 무엇이든 그 슬롯들에 던질 질문은 동일하다. 즉 문제 유형 분류(taxonomy) 없이도 공통 프레임이 성립한다.

**공통 질문 7종** (자료 슬롯에서 역산):

##### A군 — 관측 정리 (결론 내리기 전)

- **Q1. 정상 흐름 대비 이탈점** — 관측된 로그 순서가 `12_event_sequences`의 정상 경로와 어디서 갈라지는가?
- **Q2. 부재 증거** — 정상이라면 나와야 할 로그가 빠졌는가? 빠졌다면 (a) 레벨 게이팅으로 안 찍힌 것인지 (b) 실제로 그 코드가 실행되지 않은 것인지? (`analysis/sdp_frc/README.md` §4-6 "로그가 없다 ≠ 그 일이 없었다")
- **Q3. 상태 추정** — 로그 시점에 드라이버가 `log_analysis/04_state_model`의 8상태 중 어디였는가? 그 상태에서 신고된 증상이 설명되는가?
- **Q4. 커버리지 갭** — 정제된 로그 중 log_index에 매칭되지 않은 라인은? 그것이 타 모듈 로그인지, 자료 스냅샷 이후 추가된 코드인지, 인덱스 누락인지?

##### B군 — 대조

- **Q5. 알려진 결함 대조** — `10_summary_and_findings`의 CONFIRMED/PLAUSIBLE 중 부합하는 것이 있는가? (반드시 "없음"이 허용되는 형태로 물어야 한다 — 억지 매칭 유도 금지)
- **Q6. 모듈 경계 이탈** — 증거가 이 모듈 안에서 설명되는가, 아니면 `08_external_contract`/`log_analysis/06_cross_module_edges`의 외부 심볼·형제 모듈로 넘어가는가?

##### C군 — 행동 제안

- **Q7. 다음 관측 제안** — `07_debug_interfaces` 기준, 어떤 debugfs/procfs/t2d 노드를 켜거나 읽으면 이 가설을 확증/반증할 수 있는가?

C군(Q7)을 특별히 강조한다. "분석에 도움이 되는 유용한 자료"(§1 목표)에 가장 직접적으로 답하는 것은 가설 자체가 아니라 **"그것을 어떻게 확인하는가"**이며, 자료 README도 "코드 변경 제안 전에 기존 observability를 먼저 제안하라"고 명시해 자료의 의도와도 일치한다.

**호출 분할 — 관측(A군) → 가설(B·C군) 2단계**: 한 번에 전부 묻지 않고 두 호출로 나눈다. 형식적 정돈이 아니라 실질적 이유가 있다 — LLM의 최대 실패 모드는 **먼저 결론을 정하고 그에 맞는 근거만 골라 읽는 것**이다. 관측을 먼저 확정한 뒤 그 고정된 목록에서만 가설을 세우게 하면 calibration이 개선되며, `ExpertReport`의 `counter_points`·`confidence`(§5)가 형식적으로 채워지는 것을 막는 장치이기도 하다.

**프롬프트 골격** (두 호출 공통):

```text
[시스템 지침]   고정 — 역할 + analysis/sdp_frc/README.md §4 오류감소 규칙 승계
                (사실/추론/가정 구분, 모든 주장에 file:line, 모르면 모른다고,
                 추정·미검증 마커 위에 확정 결론 쌓지 않기, 칩 혼동 금지)

[전제]         자동 주입 — chip, build_assumption (<chip>/00 §2 또는 10 도입부)

[참고자료]      Stage 2 결정론적 선택 결과 (subsystem 태그 기반 02~09 + 항상 10·12)

[관측]         Stage 1 정제 로그 + 각 라인의 file:line/subsystem 태그
               ※ 매칭 실패 라인도 "미매칭"으로 명시 (Q4의 입력)

[문제 상황]     problem_text  ← 문제별 가변성이 들어가는 유일한 지점

[질문]         1차: A군(Q1~Q4) / 2차: B·C군(Q5~Q7) (+ 1차 산출물을 관측으로 주입)
```

즉 **고정 골격 + 가변 슬롯 하나** 구조다. 문제 유형이 아무리 다양해도 그 다양성은 `problem_text`가 흡수하고 프레임은 흔들리지 않는다.

1차 출력은 사용자에게 보여줄 최종물이 아니라 2차 입력용 중간 산출물이므로, 관측 사실 목록(각 항목에 근거 인용) 정도의 가벼운 형태로 충분하다. 2차 출력이 `ExpertReport`(§5)가 되며, JSON으로 받으면 `counter_points` 공백 여부 등을 기계적으로 검사해 품질 게이트를 걸 여지가 생긴다.

**미검증 가정 (실측으로 확인할 것)**:

- 2단계가 1단계보다 실제로 나은지는 측정 대상이다 — 논리적 근거는 위와 같으나 LLM 호출이 2배가 되고 1차 요약 과정에서 정보가 유실될 수 있다. 같은 입력으로 1단계/2단계를 나란히 돌려 비교한 뒤 확정하는 것이 정직한 순서다.
- 질문 7종이 매번 전부 유효한지도 미확인이다. 특히 Q3(상태 추정)은 `log_analysis/04_state_model`이 FRC 기준으로 작성돼 있어 DP 쪽에 그대로 적용되는지 확인이 필요하다.

### 프로파일 ↔ DTV_soc_driver 자료 매핑 설정 (확정, 2026-07-27)

라우팅 규칙(번호 슬롯 의미)이 서브시스템 공통이라 매핑 설정에 넣을 필요가 없다 — 파이프라인 코드에 한 번만 구현하면 된다. 매핑 설정은 `profile 이름 → module_root 경로`만 있으면 충분하다:

```yaml
DTV_FRC: analysis/sdp_frc
DTV_DP:  analysis/sdp_drm-dp
```

chip 하위 폴더는 defect의 chip 정보로 런타임에 동적 결합한다(`<module_root>/<chip>/`).

## 5. 인터페이스/계약

### Stage 3 산출물 스키마 — `ExpertReport` (확정, 2026-07-27)

전문가 1명의 산출물 형식. 여러 전문가의 `ExpertReport`를 승자 선정 없이 그대로 나열해 사용자에게 제시한다(§3). DTV_soc_driver 자료 자체의 규율(사실/추론/가정 구분, `file:line` 인용, 신뢰도 표기, 빌드설정 전제 명시, Open questions 유지 — `analysis/sdp_frc/README.md` §4)을 그대로 승계한다.

```yaml
ExpertReport:
  # ── 메타 (전문가 식별 + 전제 조건) ──
  profile_name: str            # 예: "DTV_FRC"
  chip: str                    # 예: "rheal"
  module_root: str             # 예: "analysis/sdp_frc"  (Stage 2 매핑 결과)
  build_assumption: str        # 참조 문서가 전제한 빌드설정 한 줄 인용
                                # (해당 <chip>/00_review_and_plan.md 또는 10_summary_and_findings.md 도입부에서 발췌)
                                # — 이 전제 밖에서는 결론이 무효임을 명시

  # ── 본문 (가설 여러 개 가능 — 하나로 단정 짓지 않음) ──
  hypotheses:
    - summary: str              # 한 줄 헤드라인 (여러 리포트 훑어볼 때 보는 표면)
      confidence: 높음|중간|낮음  # 이 가설이 얼마나 뒷받침되는가
      narrative: str             # 서술형 근거 — 문장마다 (사실)/(추론)/(가정) 표기
      evidence:
        - type: log_line | doc_citation
          value: str             # 로그 라인 원문 또는 "file:line"
      counter_points: [str]      # 이 가설에 반하는 정황(있다면) — 정직성 위해 비워두지 않기

  unresolved: [str]             # 이 전문가가 확인 못 한 것 (Open questions 계승)
  warnings: [str]               # 예: "로그레벨 게이팅으로 관련 로그가 안 찍혔을 수 있음",
                                 # "이 자료는 특정 시점 소스 스냅샷 — 최신 소스와 다를 수 있음"
```

**필드 설계 근거**:

- `hypotheses`가 리스트인 이유 — DTV_soc_driver `10_summary_and_findings.md` 자체가 CONFIRMED/PLAUSIBLE 여러 결함을 한 문서에 나열하는 방식이라, 전문가 한 명도 "여기 몇 가지 가능성이 있다"고 말할 수 있어야 그 스타일과 맞는다.
- `narrative`의 (사실)/(추론)/(가정) 태그는 새로 만든 규칙이 아니라 DTV_soc_driver README §4가 이미 쓰는 표기를 그대로 승계한 것.
- `evidence`를 `log_line`/`doc_citation` 두 종류로 나눈 이유 — 검증 방법이 다르다(전자는 로그를 다시 보면 되고, 후자는 소스를 grep해야 함).
- `build_assumption`을 필수 필드로 둔 이유 — 자료 자체가 "빌드설정 전제를 명시하지 않으면 결론이 다른 빌드/칩에 잘못 도용될 위험"을 강조하기 때문에, 리포트 레벨에서 강제한다.
- `counter_points`를 명시적으로 채우게 설계한 이유 — "완벽한 분석이 아니라 유용한 참고자료"라는 목표상, 스스로 반박을 못 찾으면 그것이 곧 과신 신호이기 때문.
- 실사용하면서 보완 가능 — 확정이지만 최종 고정은 아님(사용자 확인, 2026-07-27).

**예시**: `Document/신규 문제 분석 파이프라인/Stage 3 전문가 리포트 예시.md` — 실제 DTV_soc_driver 자료(rheal 칩 ioctl 락 누수 결함)를 근거로 구성한 예시 인스턴스.

## 7. 트레이드오프 & 대안

- **자동 전문가 라우팅(기존 MoE 라우터 방식) vs 사용자 지정**: 자동 라우팅을 포기하는 대신 "어떤 전문가가 관련 있는지 판단하는 것 자체가 분석의 일부"라는 원칙을 지켰다 — 자동화된 정확도보다 판단 주체(사람의 통찰·경험)를 우선한 결정.
- **승자 선정(현 파이프라인 방식) vs 동등 나열**: 신규 문제는 정답 데이터(케이스)가 없다는 전제이므로, 결론을 하나로 수렴시키지 않고 동등 나열을 채택했다.

## 9. 구현 단계

**이 절의 성격**: 구현 착수 **전**에 작성했다 — 방향을 잃지 않기 위한 지도이지 확정 계획이 아니다. 아직 정해지지 않은 것에 의존하는 항목에는 **(추정)** 마커를 붙였다. 착수 시점에 이 절을 갱신하는 것을 전제한다.

**Phase 경계의 근거**: Phase 1~2는 LLM을 쓰지 않으므로 결정론적으로 테스트·검증할 수 있다. 프롬프트 변동성이나 LLM 비용 없이 골격의 타당성(특히 로그인덱스 매칭률)을 먼저 확인할 수 있으므로, 여기를 첫 단락 경계로 삼는다.

### Phase 0 — 스캐폴딩 + 자료 접근 경로 확보

산출물:

- 신규 최상위 디렉토리 생성 (이름을 이 시점에 확정 — §10 미해결)
- 프로파일 → `module_root` 매핑 설정 파일 (§4 형식)
- DTV_soc_driver 자료 접근 경로 해석 (**§10 미해결** — 자료가 LogAA 밖 별도 저장소에 있어 운영 환경에서의 참조 방식이 정해지지 않았다. 이 Phase에서 결론이 나야 이후 전부가 막히지 않는다)

확인 체크리스트:

- [ ] 지정된 프로파일·칩으로 `<module_root>/<chip>/` 경로가 실제로 해석되고 문서 파일이 열리는가
- [ ] 자료가 없는 프로파일·칩 조합에서 명확히 실패하는가(조용히 빈 결과를 내지 않는가)

### Phase 1 — Stage 1 정제기

산출물: 포맷 파싱 → 반복/버스트 collapse → 키워드 필터 (§4). 앵커 윈도우는 제외(부가 옵션).

확인 체크리스트:

- [ ] 실제 defect 로그를 넣어 정제 전후 라인 수와 남은 내용이 타당한가
- [ ] 동일 프로파일이면 정제 결과가 재현되는가(결정론적)
- [ ] collapse가 서로 다른 이벤트를 잘못 합치지 않는가

### Phase 2 — Stage 2 결정론적 검색

산출물: 로그인덱스 정확매칭(`match_key`) → `subsystem` 태그 → 번호슬롯 규칙 기반 문서선택 (§4).

확인 체크리스트:

- [ ] **매칭률 실측** — 실제 로그에서 log_index에 매칭되는 라인 비율이 얼마인가
- [ ] 선택된 문서 집합이 사람이 봐도 타당한가(무관한 문서가 딸려오지 않는가)
- [ ] 미매칭 라인이 누락되지 않고 "미매칭"으로 보존되는가(Q4의 입력)

**이 Phase가 go/no-go 지점이다**: 매칭률이 지나치게 낮으면 Stage 2의 전제(로그인덱스로 코드 위치를 잡을 수 있다)가 흔들리므로, LLM 단계로 넘어가기 전에 재설계 여부를 판단한다. 임베딩 레이어 추가(§4에서 보류한 것)를 다시 검토할 지점도 여기다.

### Phase 3 — Stage 2 LLM 호출

산출물: 공통 질문 Q1~Q7 프롬프트, 관측(A군)/가설(B·C군) 2단계 호출, `ExpertReport` JSON 출력.

확인 체크리스트:

- [ ] **1단계 vs 2단계 실측 비교** (§4 미검증 가정) — 같은 입력으로 나란히 돌려 품질·비용을 대조
- [ ] 산출물이 §5 스키마를 실제로 채우는가(필드 누락 없이)
- [ ] `counter_points`가 형식적으로 채워지지 않는가 — 비었거나 무의미하면 프롬프트를 고칠 신호
- [ ] `build_assumption`이 참조 문서에서 올바르게 발췌되는가
- [ ] 근거로 제시된 `file:line`이 실제로 존재하는가(환각 검사)

### Phase 4 — Stage 3 조립 + 다중 전문가 병렬

산출물: 지정된 전문가 병렬 실행, `ExpertReport` 나열 제시 (§3).

확인 체크리스트:

- [ ] **두 전문가가 실제로 서로 다른 관점을 내는가** — 같은 내용만 반복하면 다중 전문가 구조의 의미가 없다. 이 설계의 핵심 가치를 직접 검증하는 항목
- [ ] 전문가 1명 지정 시에도 동일 경로로 동작하는가
- [ ] 한 전문가의 실패가 다른 전문가 결과를 죽이지 않는가(독립성)

### Phase 5 — 사용자 인터페이스 (추정)

**§10 미해결 사항에 의존**한다 — "기존 소스 수정 금지" 제약과 "사용자가 전문가를 지정하고 결과를 열람"해야 한다는 요구가 충돌한다. 기존 `frontend`를 고칠 수 없으므로 별도 UI, CLI, 또는 다른 방식이 필요하다. 방식이 정해지지 않아 이 Phase의 산출물·체크리스트는 아직 쓸 수 없다.

### Phase 순서에 대한 메모

Phase 3의 프롬프트 품질 개선은 한 번에 끝나지 않고 Phase 4 이후에도 반복될 것이다 **(추정)** — "품질 좋은 분석 결과"가 목표이므로 프롬프트 반복 개선이 실제 작업량의 상당 부분을 차지할 가능성이 높다. Phase 3을 "완료"로 못 박기보다 Phase 4로 넘어간 뒤에도 되돌아오는 것을 전제하는 편이 현실적이다.
