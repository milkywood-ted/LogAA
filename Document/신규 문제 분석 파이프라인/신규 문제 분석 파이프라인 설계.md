작성일: 2026-07-26 (최종 갱신 2026-07-28)

## 1. 목표 및 범위

### 배경

- 현재 `AnalyzingAssistant_v2`는 "유사 케이스 있음"(KB 벡터검색+패턴매칭) 경로만 구현돼 있다. 유사 이력이 아예 없는 "신규 문제"를 위한 경로는 없다 — 저장소 루트 `analysis_upgrade` 노트(현 파이프라인 이전 원 설계)에 이미 "신규 문제로 판정된 경우 ... 순수하게 사전지식만을 바탕으로 분석하는 영역 ... FRC driver source code 전체를 지식 베이스에 넣는다"는 구상이 있었으나 미구현으로 남아 있었다.
- 사내에 `/Users/tedkim/프로젝트/DTV_soc_driver`라는, Samsung DTV SoC 커널 드라이버(`sdp_frc`, `sdp_drm-dp` 등)를 칩별(rheal/pontusm/oscarp/rheam)로 심층 분석한 소스코드 분석자료가 별도 저장소로 존재하며, 이를 신규 문제 분석의 배경지식으로 활용할 수 있음을 확인했다.

### 목표

신규(미지의) 문제는 유사 이력(케이스)이 없다는 전제 위에서, **단일 확정 진단이 아니라 "분석에 도움이 되는 유용한 참고자료"를 산출**하는 것이 목표다. 하나의 결론으로 단정짓기엔 부정확 위험과 그에 따른 리스크가 크고, 디버깅은 LLM이 갖지 못한 경험·통찰이 크게 관여하는 영역이기 때문에, 여러 "분석 전문가(=분석 프로파일)"가 각자 독립적으로 분석한 결과를 사용자에게 나열해 제시하고 최종 판단은 사람이 내리게 한다.

### 범위 안

- 사용자가 지정한 1개 이상의 분석 프로파일(전문가) 각각에 대해: 프로파일별 로그 정제 → DTV_soc_driver 참고자료 기반 분석 → 결과 산출
- 여러 전문가의 산출물을 동등하게(승자 선정 없이) 사용자에게 제시

### 범위 밖 (현재 단계)

- **"적용 가능한 전문가"의 자동 판단.** 어떤 전문가가 이 문제에 관련 있는지 아는 것 자체가 분석적 통찰이므로, 자동 선정 로직을 두지 않고 전적으로 사용자 지정에 의존한다.
- **분석 결과의 case 편입.** 최종적으로는 염두에 두고 있으나(§10 확정 이력 참고), 신규 분석 자체의 품질 확보가 선행 과제이고 편입 자체는 난이도가 낮고 의존성도 단순한 별도 작업이라 지금 범위에 넣지 않는다.

## 2. 요구사항·제약

- **[제약, high] 기존 소스 수정 금지.** 신규 파이프라인은 기존 LogAA 소스코드(`AnalyzingAssistant_v2`/`backend`/`frontend`/`puller`)를 절대 수정하지 않고 새로 구축한다. 기존 코드·DTV_soc_driver 자료를 **참조**하는 것은 허용, **수정**은 금지. (사용자 명시)
- **[제약, high] 코드 위치.** LogAA 저장소 내 새 최상위 디렉토리에 구축한다(완전 별도 repo 아님 — 같은 git 히스토리·작업 디렉토리라 기존 코드·DTV_soc_driver 자료 참조가 쉽고, `Document/`·`deploy/` 체계를 재사용할 수 있어서). 디렉토리는 `TentativeDefectTriage/` 로 확정(2026-07-28).
- **[요구사항, high] 전문가 정체성 재사용.** "분석 전문가"는 새로 만드는 개념이 아니라 `AnalyzingAssistant_v2/core/profile.py`의 기존 `Profile`(`analysis_guidelines`/`prefilter_keywords`/`knowledge_refs`/`category`) 개념을 그대로 쓴다. 실사용(사내) 환경에 `DTV_FRC`, `DTV_DP` 프로파일이 이미 존재한다(로컬 dev repo의 `config/profiles/`는 비어 있음).
- **[요구사항, high] 전문가 선정은 100% 사용자 지정.** 시스템이 "적용 가능한 전문가"를 자동 판단하지 않는다 — 사용자가 1개 이상 프로파일을 직접 지정한다. 이에 따라 지정된 전문가들은 서로 조율·순서 없이 완전 독립 병렬로 실행된다.
- **[요구사항, medium] 칩 기반 자료 축소.** defect에는 이미 칩 정보가 주어지며, 이를 이용해 프로파일이 참조하는 DTV_soc_driver 자료를 칩 단위로 좁힌다 — 기존 `merge_profiles(..., chip=...)`가 `knowledge_refs`를 칩으로 필터링하는 것과 같은 축이다.
- **[제약, medium] DTV_soc_driver 자료의 성격.** 이 자료는 사례(case) 데이터가 아니라 소스 코드 분석 참고자료(reference)다. 실제 발생한 특정 문제를 가리키지 않으므로 `cases`/`patterns` 스키마로 직접 변환·임포트하지 않는다 — 전문가별 분석 단계(Stage 2)에서 배경지식으로만 주입한다.
- **[제약, medium] 프로파일 ↔ DTV_soc_driver 자료 매핑은 이름으로 자동 추론 불가.** `DTV_FRC` → `analysis/sdp_frc/<chip>/`, `DTV_DP` → `analysis/sdp_drm-dp/<chip>/`(대상 모듈 `tztv-media-sec/sdp_drm`, device flag `dp`) — 프로파일 이름과 폴더 이름이 문자열 1:1 변환이 아니므로(`DTV_DP`→`sdp_drm-dp`) 명시적 매핑 설정이 필요하다(§10 미해결 질문).

## 3. 아키텍처 개요

유사 이력 매칭(기존 Stage 2 KB search)이 필요 없다는 전제 위에서, 기존 `AnalyzingAssistant_v2`(6-Stage)보다 훨씬 단순한 3단계 파이프라인으로 설계한다.

```
[입력] problem_text, raw_logs, chip, 사용자가 지정한 전문가(프로파일) 목록 (1개 이상)
         │
         ▼  (지정된 전문가 수만큼 완전 독립 병렬 실행 — 조율/순서 없음)
┌─────────────────────────────────────────────┐
│ Stage 1 — 전문가별 로그 정제                    │
│   그 프로파일의 prefilter_keywords로 필터링      │
│                                               │
│ Stage 2 — 전문가별 분석                        │
│   입력: 정제된 로그 + problem_text              │
│        + analysis_guidelines                  │
│        + DTV_soc_driver 참고자료(프로파일→      │
│          서브시스템 매핑, chip으로 좁힌 문서)      │
│   출력: 가설 + 근거 + 사실/추론/가정 구분         │
│        + 불확실성 표기                          │
└─────────────────────────────────────────────┘
         │
         ▼
Stage 3 — 전문가별 산출물을 사용자에게 나열 제시 (승자 선정 없음)
```

기존 `AnalyzingAssistant_v2`의 MoE 앙상블(`pipeline.py`의 `moe_traversal_mode`, 전문가별 Stage1 정제 `moe_per_expert_stage1`)이 "여러 전문가 병렬 실행" 골격의 선례이긴 하나, 그 구조의 "winner 수렴 + minority 축소"는 이 파이프라인의 목적(다중 관점 동등 제시)과 반대이므로 그대로 채택하지 않는다.

## 4. 컴포넌트 설계

### Stage 1 — 전문가별 로그 정제

**구현 방식(확정, 2026-07-26)**: 기존 `AnalyzingAssistant_v2/core/log_refiner.py`(`LogRefiner`/`RefineConfig`)를 import·의존하지 않고 **완전히 새로 구현**한다 — 목적이 다르기 때문(기존은 "케이스 매칭 전제의 공통 1회 정제"이고, 이쪽은 "전문가별 독립 정제"). 다만 그 코드의 접근 방식(포맷 파서 분리, fingerprint 기반 collapse 등)은 설계 아이디어 차원에서 참고할 수 있다.

**필요 기능(확정)**:

- **포맷 파싱** — 로그 라인에서 타임스탬프·메시지를 분리한다. DTV_soc_driver `golden_capture/CAPTURE_SPEC.md`의 dmesg/debugfs `inlog`는 캡처 경로(콘솔 vs 링버퍼)와 레벨 게이팅 깊이만 다를 뿐 **라인 포맷은 동일**(`[타임스탬프][S_F] 메시지`)하므로 범용 파서 하나로 충분 — 소스별 분기 불필요(2026-07-26 정정). `mirror_log`(레지스터 접근 이력 테이블, printk 텍스트와 구조가 다름)는 `raw_logs` 입력 범위에 포함하지 않기로 확정(2026-07-27) — 파서가 다룰 필요 없음.
- **반복/버스트 collapse** — 동일 로그가 짧은 시간에 폭주할 때 압축.
- **키워드 필터** — 프로파일의 `prefilter_keywords` 기반 OR 매칭.

**부가 옵션(핵심 요구사항 아님, 필요해지면 후순위로 추가)**:

- 앵커 기반 시간 윈도우 추출.

#### 출력 크기 목표 — 약 50k 토큰 이내 (확정, 2026-07-28)

§ 발췌로 문서 측이 126,394자까지 내려오면서 컨텍스트 제약이 문서에서 **로그로 이동**했다. 이를 "정제 후 로그가 얼마나 되는지 재보자"는 **측정 과제가 아니라 Stage 1 의 설계 목표**로 다룬다 — Stage 1 은 우리가 만드는 것이므로 목표치를 정하고 그에 맞추면 된다(기존 `AnalyzingAssistant_v2` 도 `max_log_lines: 2000` · `context_strategy: truncation` 으로 같은 접근을 한다).

바운드 계산:

```text
입력 예산   ≈ 132k 토큰   (num_ctx 198,000 − max_tokens 65,535)
문서 측     ≈ 51~84k 토큰 (126,394자 ÷ 1.5~2.5자/토큰)
지침+문제   ≈  2k 토큰
──────────────────────────────
로그 몫     ≈ 51~83k 토큰 → 보수적으로 50k 토큰을 상한으로 잡는다
```

상한을 넘으면 자르거나 우선순위를 매긴다 — 어느 쪽이든 Stage 1 을 만들면서 정할 사항이다(§9 Phase 1).

**주의**: 위 토큰 환산비(1.5~2.5자/토큰)는 추정이다. 정확한 값은 실제 모델 토크나이저로 재야 하며, 도구만 있으면 사내에서 확인할 수 있다(§9 Phase 3).

### Stage 2 — 전문가별 분석

**DTV_soc_driver 자료 검색 방식(확정, 2026-07-27 / 발췌 방식으로 정정)**: 임베딩 의미검색 없이, **로그인덱스 정확매칭 + 번호슬롯 규칙 기반 문서선택 + `file:line` 조인 기반 § 발췌**의 결정론적 3단계로 처리한다.

1. **로그 앵커 매칭** — Stage 1에서 정제된 로그 라인을 `<module_root>/<chip>/11_log_index.tsv`의 `match_key` 컬럼에 대조한다(포맷 문자열의 변수부를 제거하고 리터럴로 매칭 — `analysis/sdp_frc/README.md` §4-7 방식 그대로). 매칭되면 `file:line` + `subsystem` 태그를 얻는다.
2. **문서 선택** — 00~12 번호 슬롯은 서브시스템 공통 관례임을 확인했다(00=계획, 01=아키텍처, 02=init/probe, 03=ioctl, 04=irq, 05=power, 06=command/pipeline path, 07=debug, 08=external contract, 09=framework 통합, 10=결함매트릭스, 11=로그인덱스, 12=이벤트시퀀스 — `sdp_frc`·`sdp_drm-dp` 양쪽에서 슬롯 번호가 동일함을 diff로 확인, 09만 서브시스템별 제목이 다름). 1번의 `subsystem` 태그에 대응하는 02~09 문서를 선택하고, 10·12는 항상 기본 포함한다.
3. **§ 발췌** — 선택된 문서를 통짜로 주입하지 않고 **`##`/`###` 섹션 단위로 발췌**한다. 각 § 이 인용하는 `file:line` 집합과 1번에서 관측된 `file:line` 집합이 겹치는 § 만 취한다. 문서에 `file:line` 인용이 풍부해(rheam 기준 총 1,141건, 02~09·12가 각 57~171건) 조인 키로 쓸 수 있으며, 1번에서 이미 91.6%로 검증된 것과 **같은 조인 키**를 재사용한다. 구현: `TentativeDefectTriage/material/excerpt.py`(Stage 2 의 실제 부품 — 측정용 별도 코드가 아니라 Phase 2 에서 파이프라인이 그대로 호출한다).

**질문 근거 문서 보충 (2026-07-28 추가 — 실행에서 드러난 결함 수정)**: 질문 게이팅은 "근거 파일이 존재하는가"만 보는데 § 발췌는 **관측된 코드 위치** 기준이라, 둘이 어긋나면 **근거 없이 질문만 던져진다**. 실제 실행에서 두 구멍이 확인됐다:

- Q3 근거(`log_analysis/04_state_model.md`)는 **칩 디렉토리 밖**이라 `load_docs()` 가 애초에 읽지 않았다 — FRC 에서 Q3 가 항상 던져지지만 상태 모델 정의는 **한 번도 제공되지 않았다**.
- Q7 근거(`07_debug_interfaces.md`)는 관측 위치와 겹치지 않으면 빠진다 — 실제로 빠진 채 질문만 나갔다.

이는 이 설계가 막으려던 것(근거 없는 질문 → LLM 이 추측으로 메움) 그 자체다. 수정: **던지는 질문의 근거 문서가 발췌에 전혀 기여하지 못했으면 보충한다.** 이미 § 가 뽑혔으면 그쪽이 관련 부분이므로 중복하지 않는다.

보충 방식은 크기 때문에 단계를 둔다 — 통짜로 넣으면 프롬프트가 28.5k→99.8k자로 뛴다(근거 문서 4종 합계 97k자).

1. **관측된 subsystem 을 언급하는 § 만** 선택 — 최초 설계의 "subsystem 기준 § 선택" fallback 이 여기서 제 역할을 한다.
2. 그래도 안 걸리거나 축소 효과가 없으면(80% 이상) 전문. 조각내서 맥락만 깨는 것보다 낫다.

실측: 99.8k → **66.9k자(약 44.6k 토큰)**. `04_state_model` § 5/16, `07_debug_interfaces` § 5/28 로 축소되고 `06_cross_module_edges` 만 전문으로 갔다. 로그 예산 50k 토큰을 더해도 약 95k/132k 로 여유가 있다.

**§ 발췌 구현 시 주의**:

- **라인 번호가 정확히 일치하지 않는다.** 로그인덱스는 `sdp_frc_ioctl.c:279` 형태의 단일 라인인데, 문서는 `:272-287`(범위) · `:280` · `(:285)` 같은 축약형으로 인용한다(DTV_soc_driver에 `normalize_paths.py`가 있는 이유). 따라서 **파일 단위로 매칭하고 라인 근접도로 순위**를 매겨야 한다 — 라인 동등 비교는 대부분 실패한다.
- **통짜 유지 대상**: `10_summary_and_findings`(결함매트릭스)와 `11_log_triage`는 인용이 각 15·17건뿐이지만 큐레이션된 의미 해석이라 쪼개면 맥락이 깨진다. 둘 다 작아(rheal 기준 6.9k+6.1k자) 통짜로 둬도 예산 부담이 없다.
- **fallback (구현에서 확정)**: exact/near 로 § 를 하나도 못 건진 **파일에 한해서만** 같은 파일을 인용한 § 를 끌어온다(`file_only` 등급). 같은 파일이라는 이유로 전부 끌어오면 발췌 의미가 사라지므로, 건질 게 없을 때만 쓴다. 최초 설계의 "subsystem 기준 § 선택"보다 정밀하고, subsystem→§ 매핑이라는 추가 규칙도 필요 없다.
- **window(라인 근접 허용 폭)가 주입량을 크게 좌우한다** — 아래 실측 참고. 기본값 10.

**왜 통짜 주입이 아닌가(2026-07-27 정정)**: 최초 설계는 "각 문서가 수십~수백 줄로 짧다"는 근거로 문서 전체 주입을 택했다. 개별 문서는 실제로 짧지만(81~451줄) **분석 단위를 잘못 잡은 것**이었다 — 실제 제약은 문서 하나가 아니라 선택된 문서들의 합계다. 프로브 실측(아래)에서 rheam 문서 전체가 258,595자로 나와, `num_ctx: 198000` · `max_tokens: 65535`(입력 여유 약 133k 토큰) 환경에서 문서만으로 예산을 소진하는 것이 확인됐다. 사용자의 최초 판단("발췌 검색이 맞을 것 같다")이 옳았고, 그것을 문서 단위 선택으로 좁힌 것이 오류였다.

**소스 직접 접근(grep)은 현재 도입하지 않음 (확정, 2026-07-28)**: `log_analysis/02_triage_recipe.md` §1 은 소스 grep 을 **시나리오 A(우선)** 로 두고 양 모듈 README 모두 "소스가 최종 근거, 자료는 스냅샷"이라고 명시한다. 소스도 실제로 저장소에 있다(`tztv-media-sec/`). 그래도 넣지 않는다:

- **분석 문서가 이미 소스를 읽은 결과물이다.** 시나리오 A 가 소스를 보라는 이유("감싼 함수·if조건을 읽어 무슨 상태에서 찍히는지 파악")를 문서가 이미 수행해 기록했다. 소스의 한계 효용은 ① 문서가 그 위치를 안 다룰 때 ② 문서가 소스와 어긋났을 때 ③ 문서가 요약해 버린 세부가 필요할 때로 좁다.
- **①은 실측에서 없었다** — fallback 파일 0종, 문서에 인용이 전혀 없는 관측 파일 0종. 관측 위치를 문서가 전부 덮었다.
- **②는 약한 논거다** — 저장소 소스도 스냅샷이라 grep 해도 기기 실제 빌드와의 어긋남은 남는다. 잡히는 건 "문서가 같은 스냅샷을 잘못 옮겼는지"뿐이고 그건 `verify_citations.py` 가 이미 강제한다.
- **반대 논거가 더 세다** — DP README §4.3 은 **소스를 잘못 읽어 낸 실제 사고 4건**(파일명으로 역할 오분류, `return 0` 스텁을 동작으로 2회 기록, IRQ 핸들러 위치 오판, 선언만 보고 호출 추정)을, §4.1 은 인코딩 때문에 파일이 통째로 안 보여 "존재하지 않는다"고 기록한 사고를 남겼다. 분석 문서는 그 실수들을 검증 도구로 걸러낸 산출물이다. **원시 C 를 벌크로 주입하면 검증 없이 같은 실패 모드에 재노출된다.** 레시피의 시나리오 A 는 "검증하며 정독하는" 설정을 전제하는데 이 파이프라인은 "컨텍스트를 자동 조립하는" 설정이라 다르다.
- 컨텍스트 예산이 이미 로그 쪽으로 빠듯한 것도 이유다(§4 축소율 실측).

**나중에 넣는다면 벌크 주입이 아니라 좁은 검증 도구로** — 가설이 특정 코드 사실에 걸려 있을 때(예: "이 early-return 이 `mutex_unlock` 을 건너뛴다") 그 함수만 확인하는 방식. 자료가 말한 "소스가 최종 근거"도 이 의미(검증)이며 벌크 정독을 뜻하지 않는다. 도입 시 **`LC_ALL=C grep -a` 필수** — plain grep 은 ISO-8859/EUC-KR 파일을 무경고로 스킵한다(DP README §4.1).

**임베딩 의미검색은 현재 도입하지 않음(확정 사유)**: 의미검색이 실제로 푸는 문제("자연어 질의로 어느 서브시스템/문서를 볼지 찾기")가 이 설계엔 없다 — 사용자가 전문가(프로파일)를 지정하는 순간 서브시스템이 이미 확정되기 때문. 로그→코드 매칭은 포맷 변수만 다른 정확매칭 문제라 의미검색보다 리터럴 매칭이 더 적합하고, § 발췌도 `file:line` 조인으로 결정론적으로 된다. 다만 §  발췌의 손실이 큰 것으로 드러나면(fallback 비중이 높거나 필요한 맥락이 잘려나가면) 문서 내 chunk 검색은 임베딩이 실제로 잘 푸는 문제이므로, 그때 이 레이어 위에 얹는 것을 재검토한다.

#### 자료 규약과 검증 (확정, 2026-07-28)

소비자 코드(`excerpt.py` 등)는 분석자료의 여러 규약에 의존한다 — TSV 컬럼 순서, 통짜 유지 파일명, 레벨 어휘, 인용 형식, 문서 슬롯 번호. 이 가정이 코드에 하드코딩돼 있으면 자료 갱신 시 **조용히 나빠진다**(에러가 아니라 "발췌가 덜 되거나 엉뚱하게 되는" 형태). 실제로 커밋 `d4012348f`(인덱스 904→870행)를 알아챈 것은 우연히 측정 재현을 시도했기 때문이었다.

**의존성을 성격에 따라 세 부류로 나눈다:**

| 부류 | 예 | 소유 | 자료 갱신 시 |
| --- | --- | --- | --- |
| ① **설정값** | 통짜 유지 파일명, 레벨 어휘, TSV 컬럼, 문서 슬롯, driver tag | 자료(매니페스트) | **자동 적응** — 사람 개입 불필요 |
| ② **형식 파싱** | 인용 정규식, 헤딩 파싱 | 소비자 코드 | `schema_version` 불일치로 **명시적 실패** → 사람이 수정 |
| ③ **소비자 정책** | `window`, fallback 규칙, 예산 목표 | 우리 | 영향 없음 |

③을 자료 쪽에 두지 않는 이유: 자료 세트에 소비자 코드를 통째로 넣으면 정책까지 얼어붙어, 발췌 품질 튜닝(이 파이프라인의 주된 작업)이 막힌다.

**매니페스트** (`MANIFEST.json`, 자료 저장소 루트): ①을 선언한다. 초안은 `verify_material.py --emit-manifest` 로 생성한다 — 소비자가 무엇을 가정하는지가 그대로 파일이 되므로 자료 쪽에서 검토·수정하면 된다. **없으면 내장 기본값으로 동작하되 경고**한다 — 자료 저장소 수정 가능 여부에 파이프라인이 막히지 않도록.

**검증기** (`TentativeDefectTriage/material/verify_material.py`): 자료를 pull 한 뒤 또는 파이프라인 실행 전에 돌린다. LLM 호출 없이 파일만 읽어 가볍다. 세 층을 본다:

1. **선언 ↔ 실제** — 매니페스트가 말한 컬럼·파일이 실재하는가
2. **선언 ↔ 소비자 능력** — `schema_version` 을 아는가, 모르는 레벨 어휘·문서 슬롯이 있는가
3. **기준선 대비 변화** — 인덱스 행수·섹션·인용 수·문서 크기를 `material_baseline.json` 에 기록해두고 델타를 보고. `d4012348f` 를 즉시 잡았을 층이다

종료 코드: `0` 이상없음 / `1` 경고(사람 판단 필요) / `2` 오류(구조 위반 — 고치기 전엔 결과를 믿으면 안 됨).

**동작 확인**: 실제 자료 8개 대상(FRC·DP 각 4칩) 구조 이상 없음. 자료 복사본에 변경 4종을 주입해 전부 감지됨 — 컬럼명 변경(오류), 통짜유지 파일명 변경·모르는 레벨(`TRACE`)·모르는 슬롯(`13_*.md`)(경고), 그리고 세 칩의 기준선 델타.

**변화가 곧 오류는 아니다.** 자료 갱신은 대체로 개선이므로(아래) 검증기는 "달라졌다"를 드러내는 데까지만 책임지고, 의도된 변화인지는 사람이 판단해 `--update-baseline` 으로 받아들인다.

#### 자료 갱신과 측정치 (2026-07-28)

측정 재현을 시도하다가 자료가 바뀌어 기록한 수치가 낡은 것을 발견했다 — 커밋 `d4012348f`("extract_logs: 주석 처리된 로그·미빌드 파일 유입 수정 + 로그 인덱스 재생성")로 rheam FRC 인덱스가 **904행 → 870행**이 됐다(문서 총량도 258,595 → 258,770자). 이전 측정은 주석 처리된 로그와 미빌드 파일의 로그가 섞인 인덱스로 잰 것이었다 — `T2D` 와 같은 부류의 오염이 하나 더 있었던 셈이다. 현재 자료로 재측정했고 결론은 세 번 모두 유지됐다(축소율 둔감성).

**여기서 필요한 조치는 "실측치에 자료 커밋 해시를 병기한다" 하나다.** 이 문서의 수치는 그렇게 기록한다.

**자료 갱신 자체는 파이프라인에서 신경 쓸 문제가 아니다** — 갱신은 대체로 **개선**이기 때문이다(위 커밋이 한 일은 틀린 항목의 제거였다). 버전을 고정하면 파이프라인이 계속 틀린 자료를 쓰게 되므로 오히려 해가 된다. 리포트 재현이 요구되는 성격의 산출물도 아니다(사람이 읽고 판단에 쓰는 참고자료이며, 결과가 달라지면 보통 새 자료가 더 맞다). `ExpertReport.build_assumption`(§5)이 필수인 것과는 성격이 다르다 — 빌드 설정 전제는 잘못 적용되면 다른 칩에 틀린 결론을 가져다 쓰는 실질적 위험이 있지만, 자료 버전은 같은 코드를 더/덜 잘 기술한 차이일 뿐이다.

따라서 리포트에 사용 자료 버전을 한 줄 남기는 정도로 충분하고, 이것이 자료 접근 방식을 좌우하지는 않는다(§10 "자료 접근 경로" 참고).

**최초 측정의 오염과 정정(2026-07-27)**: 첫 측정은 관측 집합에 `T2D` 레벨 항목을 포함해 만들었는데, `analysis/sdp_drm-dp/README.md` §4.6 에 따르면 **`level` 이 `T2D` 인 행은 dmesg 기대 로그가 아니다**(전부 `#ifdef CONFIG_T2D_DEBUGD` 안이라 커널 설정에 따라 컴파일 자체가 빠지고, `PRINT_T2D` 정의도 저장소 밖). 규모가 작지 않다 — **FRC rheam 904행 중 362행(40%)이 T2D** 이고, 특히 `debug_t2d` subsystem(377행)이 인덱스 최대 규모여서 제외 없이는 subsystem 분포가 실제 dmesg 와 무관하게 왜곡된다. 두 프로브에 `--exclude-level`(기본 `T2D`)을 추가했다. 축소율 결론 자체는 바뀌지 않았다(둔감성 때문).

**window 기본값을 40 → 10 으로 낮췄다.** 0 이 가장 작지만, 분석 문서와 로그인덱스는 각각 생성되므로 소스 변경 시 라인이 어긋날 수 있다(자료 자체가 경고하는 stale 문제). 10 은 드리프트를 흡수하면서 예산에도 든다.

**제약이 문서에서 로그로 이동했다**: 문서가 126k자로 내려오면서, 이제 함께 주입될 정제 로그의 크기가 관건이 됐다. 모집단 1,190줄 규모면 로그만 100k자 안팎이라 합산 시 다시 빠듯해질 수 있다 — **Stage 1 정제가 로그를 얼마나 줄이는지**가 다음 확인 대상이다(§9 Phase 1·2).

즉 **DP 전문가는 Q1·Q2·Q4·Q5·Q7 은 되지만 Q3·Q6 은 근거가 없다.** 프롬프트가 근거 없는 질문을 던지면 LLM 이 추측으로 메우므로, 자료가 없는 질문은 **명시적으로 생략하고 그 사실을 리포트에 남겨야 한다**(`ExpertReport.unresolved`).

**칩·모듈별 로그 접두가 다르다** — Stage 1 파서와 프로브 `--driver-tag` 에 직결된다.

- FRC: `[S_F]` (레벨 게이팅 로그). 그 외 `pr_err` 등은 접두 없이 무조건 출력.
- DP: **`[DRM-DP]`**(뒤에 공백 포함) 이나 **oscarp 만 `[DRM-DP:I]`**. 두 변형을 함께 잡으려면 여는 괄호까지만 쓰는 `\[DRM-DP` 가 안전하다. (`[sdp_dp]` 는 접두가 아니라 일부 포맷 문자열의 일부 — 태그로 쓰면 안 된다. 최초 프로브 README 의 오기를 정정했다.)
- 레벨 어휘 자체가 다르다 — FRC: ALERT/ERROR/DEFAULT/INFORM/COMMENT, DP: ERROR/INFO/WARN/ALERT/DEFAULT. Q2(부재 판단)는 모듈별 체계를 전제로 해야 한다.

**DP 고유 함정** (`sdp_drm-dp/README.md` §4.6·§4.7 — Q2·Q5 에 직접 영향):

- `dp_pr_*` 는 dmesg 와 **vlogger 에 이중 출력**된다(태그 `SLSI-DRM-DP`) — dmesg 에 없어도 vlogger 엔 있을 수 있다. "로그 부재"를 단정하면 안 되는 추가 이유.
- **rheam DP 는 로그에 자기 칩명 대신 `PontusM` 을 찍는다** — 로그로 칩을 추정하면 오판한다(칩은 메타로 받는다는 원칙의 근거).
- `-EPERM` 은 권한 오류가 아니라 **런타임 PM 참조 획득 실패**(전원 상태 문제)다. `-EINVAL`=미구현 콜백, `-ESRCH`=미등록 프로퍼티.

**`T2D` 레벨 제외 (구현 반영)**: `level` 이 `T2D` 인 행은 매칭 대상에서 제외한다 — `#ifdef CONFIG_T2D_DEBUGD` 게이트라 컴파일 자체가 빠질 수 있고 출력 경로도 미확인이다. 규모가 크다(FRC rheam 40%, DP rheam 216행). 두 프로브의 `--exclude-level` 기본값.

**`_fact_extract.txt`/`_func_inventory.txt`의 취급 (재검토 필요)**: 최초에 "생산 중간 산출물"로 소비 대상에서 제외했으나, DP README 는 이를 **자료 지도에 소비 대상으로 등재**했다(기계 인벤토리 — 함수 목록 / 락·외부호출·할당·**게이트** 패턴). 특히 `_fact_extract.txt`(25k자)의 GATE 필드는 `defined(CONFIG_T2D_DEBUGD)`·`CHIP_TEST` 같은 값을 담아 §4.4 "존재 ≠ 동작" 판단에 직접 쓰인다 — Q2·Q5 에 유용할 수 있다. `_func_inventory.txt`(67k자)는 통짜 주입에는 크므로 조회용이 적절하다. **DP 에만 있어 FRC 와 비대칭**이라는 점도 고려해 편입 여부를 결정한다(§10 미해결).

#### Stage 2 LLM 호출 구조 (확정, 2026-07-27)

**공통 질문이 성립하는 근거**: 신규 문제는 유형이 사전에 파악되지 않으므로 "문제 유형별 질문 세트"를 만들 수 없다. 그런데도 공통 질문이 성립하는 이유는 문제들이 서로 비슷해서가 아니라 **참고자료의 모양이 고정돼 있어서**다 — 00~12 번호 슬롯이 각각 답할 수 있는 질문 종류가 정해져 있으므로, 문제가 무엇이든 그 슬롯들에 던질 질문은 동일하다. 즉 문제 유형 분류(taxonomy) 없이도 공통 프레임이 성립한다.

**공통 질문 7종** (자료 슬롯에서 역산):

##### A군 — 관측 정리 (결론 내리기 전)

- **Q1. 정상 흐름 대비 이탈점** — 관측된 로그 순서가 `12_event_sequences`의 정상 경로와 어디서 갈라지는가?
- **Q2. 부재 증거** — 정상이라면 나와야 할 로그가 빠졌는가? 빠졌다면 (a) 레벨 게이팅으로 안 찍힌 것인지 (b) 실제로 그 코드가 실행되지 않은 것인지? (`analysis/sdp_frc/README.md` §4-6 "로그가 없다 ≠ 그 일이 없었다")
- **Q3. 상태 추정** — 로그 시점에 드라이버가 `log_analysis/04_state_model`의 8상태 중 어디였는가? 그 상태에서 신고된 증상이 설명되는가?
- **Q4. 커버리지 갭** — 정제된 로그 중 log_index에 매칭되지 않은 라인은? 그것이 타 모듈 로그인지, 자료 스냅샷 이후 추가된 코드인지, 인덱스 누락인지?

##### B군 — 대조

- **Q5. 알려진 결함 대조** — `10_summary_and_findings`의 CONFIRMED/PLAUSIBLE 중 부합하는 것이 있는가? (반드시 "없음"이 허용되는 형태로 물어야 한다 — 억지 매칭 유도 금지)
- **Q6. 모듈 경계 이탈** — 증거가 이 모듈 안에서 설명되는가, 아니면 `08_external_contract`/`log_analysis/06_cross_module_edges`의 외부 심볼·형제 모듈로 넘어가는가?

##### C군 — 행동 제안

- **Q7. 다음 관측 제안** — `07_debug_interfaces` 기준, 어떤 debugfs/procfs/t2d 노드를 켜거나 읽으면 이 가설을 확증/반증할 수 있는가?

C군(Q7)을 특별히 강조한다. "분석에 도움이 되는 유용한 자료"(§1 목표)에 가장 직접적으로 답하는 것은 가설 자체가 아니라 **"그것을 어떻게 확인하는가"**이며, 자료 README도 "코드 변경 제안 전에 기존 observability를 먼저 제안하라"고 명시해 자료의 의도와도 일치한다.

**호출 분할 — 관측(A군) → 가설(B·C군) 2단계**: 한 번에 전부 묻지 않고 두 호출로 나눈다. 형식적 정돈이 아니라 실질적 이유가 있다 — LLM의 최대 실패 모드는 **먼저 결론을 정하고 그에 맞는 근거만 골라 읽는 것**이다. 관측을 먼저 확정한 뒤 그 고정된 목록에서만 가설을 세우게 하면 calibration이 개선되며, `ExpertReport`의 `counter_points`·`confidence`(§5)가 형식적으로 채워지는 것을 막는 장치이기도 하다.

**프롬프트 골격** (두 호출 공통):

```text
[시스템 지침]   고정 — 역할 + analysis/sdp_frc/README.md §4 오류감소 규칙 승계
                (사실/추론/가정 구분, 모든 주장에 file:line, 모르면 모른다고,
                 추정·미검증 마커 위에 확정 결론 쌓지 않기, 칩 혼동 금지)

[전제]         자동 주입 — chip, build_assumption (<chip>/00 §2 또는 10 도입부)

[참고자료]      Stage 2 § 발췌 결과 (file:line 조인으로 뽑은 섹션 + 통짜 유지 10·11)
               ※ 예산 때문에 뺀 문서·섹션이 있으면 그 사실을 명시 —
                 LLM 이 "안 본 것"을 "없는 것"으로 오해하지 않도록

[관측]         Stage 1 정제 로그 + 각 라인의 file:line/subsystem 태그
               ※ 매칭 실패 라인도 "미매칭"으로 명시 (Q4의 입력)
               ※ file:line 후보가 복수인 라인은 후보 전체를 명시 (실측 31.2%)

[문제 상황]     problem_text  ← 문제별 가변성이 들어가는 유일한 지점

[질문]         1차: A군(Q1~Q4) / 2차: B·C군(Q5~Q7) (+ 1차 산출물을 관측으로 주입)
```

즉 **고정 골격 + 가변 슬롯 하나** 구조다. 문제 유형이 아무리 다양해도 그 다양성은 `problem_text`가 흡수하고 프레임은 흔들리지 않는다.

1차 출력은 사용자에게 보여줄 최종물이 아니라 2차 입력용 중간 산출물이므로, 관측 사실 목록(각 항목에 근거 인용) 정도의 가벼운 형태로 충분하다. 2차 출력이 `ExpertReport`(§5)가 되며, JSON으로 받으면 `counter_points` 공백 여부 등을 기계적으로 검사해 품질 게이트를 걸 여지가 생긴다.

**미검증 가정 (실측으로 확인할 것)**:

- 2단계가 1단계보다 실제로 나은지는 측정 대상이다 — 논리적 근거는 위와 같으나 LLM 호출이 2배가 되고 1차 요약 과정에서 정보가 유실될 수 있다. 같은 입력으로 1단계/2단계를 나란히 돌려 비교한 뒤 확정하는 것이 정직한 순서다.
- 질문 7종이 매번 전부 유효한지도 미확인이다. 특히 Q3(상태 추정)은 `log_analysis/04_state_model`이 FRC 기준으로 작성돼 있어 DP 쪽에 그대로 적용되는지 확인이 필요하다.

### 프로파일 ↔ DTV_soc_driver 자료 매핑 설정 (확정, 2026-07-27)

라우팅 규칙(번호 슬롯 의미)이 서브시스템 공통이라 매핑 설정에 넣을 필요가 없다 — 파이프라인 코드에 한 번만 구현하면 된다. 매핑 설정은 `profile 이름 → module_root 경로`만 있으면 충분하다:

```yaml
# 자료 저장소 루트 (서버에 clone 해둔 위치)
material_root: ~/SamsungDTV_Analysis

# 프로파일 → module_root (material_root 기준 상대경로)
profiles:
  DTV_FRC: analysis/sdp_frc
  DTV_DP:  analysis/sdp_drm-dp
```

chip 하위 폴더는 defect의 chip 정보로 런타임에 동적 결합한다(`<material_root>/<module_root>/<chip>/`).

`material_root` 를 설정으로 둔 이유: 자료는 LogAA 밖의 별도 저장소이고, 배포 대상은 `~/LogAA` 를 `git pull` 하는 리눅스 서버(`deploy/README.md`)다. 자료 저장소도 서버에 clone 해두고 같은 방식으로 갱신하면 되며, 파이프라인은 경로만 알면 된다 — submodule 결합은 불필요하다(§10).

### Stage 3 산출물 스키마 — `ExpertReport` (확정, 2026-07-27)

전문가 1명의 산출물 형식. 여러 전문가의 `ExpertReport`를 승자 선정 없이 그대로 나열해 사용자에게 제시한다(§3). DTV_soc_driver 자료 자체의 규율(사실/추론/가정 구분, `file:line` 인용, 신뢰도 표기, 빌드설정 전제 명시, Open questions 유지 — `analysis/sdp_frc/README.md` §4)을 그대로 승계한다.

```yaml
ExpertReport:
  # ── 메타 (전문가 식별 + 전제 조건) ──
  profile_name: str            # 예: "DTV_FRC"
  chip: str                    # 예: "rheal"
  module_root: str             # 예: "analysis/sdp_frc"  (Stage 2 매핑 결과)
  build_assumption: str        # 참조 문서가 전제한 빌드설정 한 줄 인용
                                # (해당 <chip>/00_review_and_plan.md 또는 10_summary_and_findings.md 도입부에서 발췌)
                                # — 이 전제 밖에서는 결론이 무효임을 명시

  # ── 본문 (가설 여러 개 가능 — 하나로 단정 짓지 않음) ──
  hypotheses:
    - summary: str              # 한 줄 헤드라인 (여러 리포트 훑어볼 때 보는 표면)
      confidence: 높음|중간|낮음  # 이 가설이 얼마나 뒷받침되는가
      narrative: str             # 서술형 근거 — 문장마다 (사실)/(추론)/(가정) 표기
      evidence:
        - type: log_line | doc_citation
          value: str             # 로그 라인 원문 또는 "file:line"
          # 코드 위치가 하나로 특정되지 않을 때(실측 31.2%) 후보 전체를 담는다.
          # 비었거나 1개면 단일 특정, 2개 이상이면 "이 중 하나"라는 뜻 —
          # 임의로 하나를 골라 value 에 확정 표기하지 말 것.
          candidates: [str]      # 선택: 동률 후보 file:line 목록
      counter_points: [str]      # 이 가설에 반하는 정황(있다면) — 정직성 위해 비워두지 않기

  unresolved: [str]             # 이 전문가가 확인 못 한 것 (Open questions 계승)
  warnings: [str]               # 예: "로그레벨 게이팅으로 관련 로그가 안 찍혔을 수 있음",
                                 # "이 자료는 특정 시점 소스 스냅샷 — 최신 소스와 다를 수 있음"
```

**필드 설계 근거**:

- `hypotheses`가 리스트인 이유 — DTV_soc_driver `10_summary_and_findings.md` 자체가 CONFIRMED/PLAUSIBLE 여러 결함을 한 문서에 나열하는 방식이라, 전문가 한 명도 "여기 몇 가지 가능성이 있다"고 말할 수 있어야 그 스타일과 맞는다.
- `narrative`의 (사실)/(추론)/(가정) 태그는 새로 만든 규칙이 아니라 DTV_soc_driver README §4가 이미 쓰는 표기를 그대로 승계한 것.
- `evidence`를 `log_line`/`doc_citation` 두 종류로 나눈 이유 — 검증 방법이 다르다(전자는 로그를 다시 보면 되고, 후자는 소스를 grep해야 함).
- `candidates`를 추가한 이유(2026-07-27 실측 반영) — 프로브 측정에서 매칭 라인의 **31.2%가 복수 `file:line`을 가리킨다**는 것이 확인됐다. 단일 `value` 만 두면 LLM이 세 번 중 한 번은 후보 중 하나를 임의로 골라 확정처럼 제시하게 되며, 이는 자료 README §4-1이 경고하는 오류(함수 경계 오독으로 실제 오판이 발생한 사례)와 같은 종류다. 모호성을 스키마 레벨에서 드러내 은폐를 구조적으로 막는다.
- `build_assumption`을 필수 필드로 둔 이유 — 자료 자체가 "빌드설정 전제를 명시하지 않으면 결론이 다른 빌드/칩에 잘못 도용될 위험"을 강조하기 때문에, 리포트 레벨에서 강제한다.
- `counter_points`를 명시적으로 채우게 설계한 이유 — "완벽한 분석이 아니라 유용한 참고자료"라는 목표상, 스스로 반박을 못 찾으면 그것이 곧 과신 신호이기 때문.
- 실사용하면서 보완 가능 — 확정이지만 최종 고정은 아님(사용자 확인, 2026-07-27).

**예시 2종**:

- `Stage 3 전문가 리포트 예시.md` — 스키마를 손으로 채운 인스턴스(rheal ioctl 락 누수 근거).
- `실행 예시 — 근거 보충 전후 비교.md` — **파이프라인을 실제로 돌려** 나온 리포트 2개. 질문 근거 보충 수정 전후를 비교한다. 입력 픽스처는 `TentativeDefectTriage/fixtures/`. **답한 것이 운영 모델이 아니고 정답을 알고 답했으므로 운영 품질의 근거로 쓰면 안 된다** — 그 한계는 문서 안에 명시돼 있다.

## 7. 트레이드오프 & 대안

- **자동 전문가 라우팅(기존 MoE 라우터 방식) vs 사용자 지정**: 자동 라우팅을 포기하는 대신 "어떤 전문가가 관련 있는지 판단하는 것 자체가 분석의 일부"라는 원칙을 지켰다 — 자동화된 정확도보다 판단 주체(사람의 통찰·경험)를 우선한 결정.
- **승자 선정(현 파이프라인 방식) vs 동등 나열**: 신규 문제는 정답 데이터(케이스)가 없다는 전제이므로, 결론을 하나로 수렴시키지 않고 동등 나열을 채택했다.

## 9. 구현 단계

**이 절의 성격**: 구현 착수 **전**에 작성했다 — 방향을 잃지 않기 위한 지도이지 확정 계획이 아니다. 아직 정해지지 않은 것에 의존하는 항목에는 **(추정)** 마커를 붙였다. 착수 시점에 이 절을 갱신하는 것을 전제한다.

**Phase 경계의 근거**: Phase 1~2는 LLM을 쓰지 않으므로 결정론적으로 테스트·검증할 수 있다. 프롬프트 변동성이나 LLM 비용 없이 골격의 타당성(특히 로그인덱스 매칭률)을 먼저 확인할 수 있으므로, 여기를 첫 단락 경계로 삼는다.

### Phase 0 — 스캐폴딩 + 자료 경로 설정

산출물:

- 신규 최상위 디렉토리 생성 (이름을 이 시점에 확정 — §10 미해결)
- 설정 파일 — `material_root` + 프로파일 → `module_root` 매핑 (§4 형식)
- 서버에 자료 저장소 clone (사내 서버에서 pull 가능한지만 확인하면 된다)
- **`probe/` 4개 파일을 묶음으로 이동** — 아래 참고

#### `probe/` 파일 이동 — 쪼개지 말 것

현재 `Document/신규 문제 분석 파이프라인/probe/` 에 있는 4개 파일은 **상호 import 로 묶인 한 덩어리**다:

```text
verify_material.py → excerpt, material_contract, probe_match_rate
excerpt.py         → probe_match_rate
make_fixtures.py   → probe_match_rate
```

따라서 **`excerpt.py` 만 파이프라인으로 옮기는 것은 불가능하다** — `verify_material.py` 가 깨지고, `excerpt.py` 는 `Document/` 안으로 되짚어 import 해야 한다. 통째로 옮기거나 통째로 두거나 둘 중 하나다.

**통째로 옮기는 쪽을 택한다.** 파이프라인 런타임 코드가 문서 폴더에 있는 것은 구조적으로 어색하고(배포 서버가 `~/LogAA` 전체를 pull 하므로 동작 자체는 문제없지만), 나중에 이 코드를 손볼 사람이 `Document/` 를 뒤질 이유가 없다. 이동 후 `Document/` 는 문서만 남는다.

매니페스트(§4)는 이 판단과 무관하다 — 자료별 설정을 코드 밖으로 빼는 것이지 코드 위치에는 영향이 없다. 다만 매니페스트로 자료별 특수성이 빠지면 이 도구들은 "어떤 자료든 다루는 범용 도구"가 되므로, 특정 자료에 붙여둘 이유는 더 줄어든다.

확인 체크리스트:

- [ ] 지정된 프로파일·칩으로 `<module_root>/<chip>/` 경로가 실제로 해석되고 문서 파일이 열리는가
- [ ] 자료가 없는 프로파일·칩 조합에서 명확히 실패하는가(조용히 빈 결과를 내지 않는가)
- [ ] 이동 후 4개 파일의 import 가 전부 성립하는가 (`verify_material.py` 가 실행되면 나머지도 로드된 것)
- [ ] `material_baseline.json` 경로가 이동에 따라가는가 (`verify_material.py` 는 스크립트 옆에서 찾는다)

### Phase 1 — Stage 1 정제기

산출물: 포맷 파싱 → 반복/버스트 collapse → 키워드 필터 (§4). 앵커 윈도우는 제외(부가 옵션).

확인 체크리스트:

- [x] **collapse가 서로 다른 이벤트를 잘못 합치지 않는가** — 지문이 16진값만 마스킹하도록 설계. 정수만 다른 7줄은 전부 보존, 16진 주소만 다른 8줄은 축약됨을 합성 로그로 확인
- [x] **동일 프로파일이면 정제 결과가 재현되는가** — 5회 반복 실행 해시 동일
- [x] **출력이 약 50k 토큰 이내인가** — 40,000줄(2.5MB) 입력에서 49,973토큰으로 수렴. 초과 시 **가운데를 버리고 머리·꼬리 유지**로 확정(아래)
- [ ] 실제 defect 로그로 정제 전후가 타당한가 — 사내 확인 필요(합성 로그로는 동작만 검증)

**구현**: `TentativeDefectTriage/refine/refine.py`

**collapse 지문 설계(확정)**: 16진값(`0x…`, 긴 hex 런)만 마스킹하고 **정수는 건드리지 않는다**. 드라이버 로그는 정수에 의미를 담기 때문이다 — rheam 인덱스 실측에서 `idx is invalid %d %d`, `CUR OP MODE = %x (%d)`, `FRC CLK DIVIDE OPT : %d` 같은 포맷이 확인됐고, 정수를 마스킹하면 서로 다른 idx·모드·옵션이 한 줄로 합쳐져 **디버깅 대상 그 자체가 사라진다**. 반면 `0x%x` 주소·`regaddr:0x%px` 는 호출마다 달라지는 게 정상이라 마스킹해도 이벤트 동일성이 유지된다. 연속 중복은 지문이 아니라 **본문 완전 일치**로만 합친다.

**예산 초과 처리(확정)**: **가운데를 버리고 머리·꼬리를 남긴다.** 머리는 부팅·초기화 맥락, 꼬리는 실패 시점을 담는 경우가 많고 어느 쪽이 중요한지는 문제마다 다르므로, 한쪽만 남기면 절반의 문제에서 틀린다(그리고 burst collapse 가 이미 가운데의 반복을 줄여둔 상태다). **버린 사실과 규모를 경고로 남겨** 다운스트림이 "안 본 것"을 "없는 것"으로 오해하지 않게 한다 — 프롬프트 `[참고자료]` 슬롯의 누락 명시 원칙(§4)과 같은 이유다.

### Phase 2 — Stage 2 결정론적 검색

산출물: 로그인덱스 정확매칭(`match_key`) → `subsystem` 태그 → 번호슬롯 규칙 기반 문서선택 → `file:line` 조인 기반 § 발췌 (§4).

확인 체크리스트:

- [x] **매칭률 실측** — 91.6%(모집단 기준, FRC/rheam). 사전 기준 통과 (§4 실측 결과)
- [x] **§ 발췌 후 크기가 예산 안에 들어오는가** — window=10 기준 126,394자(2.0배 축소), 입력 여유 약 133k 토큰 안에 듦. **단 합성 관측집합 기준이라 지표(indicative)** — 실제 로그로 재확인 필요
- [x] `file:line` 인용이 안 걸려 fallback으로 넘어가는 비중 — fallback 파일 0종, 미인용 관측 파일 0종 → 정밀도 양호
- [ ] **실제 로그로 발췌 크기 재확인** — `excerpt.py --log ... --index ...` (사내)
- [ ] **Stage 1 정제 후 로그 크기 + 발췌 문서 합산이 예산에 드는가** — 제약이 문서에서 로그로 이동했다(§4)
- [ ] 발췌된 § 집합이 사람이 봐도 타당한가(무관한 섹션이 딸려오지 않는가) — 자수로는 알 수 없어 육안 확인 필요
- [ ] 미매칭 라인이 누락되지 않고 "미매칭"으로 보존되는가(Q4의 입력)

**이 Phase는 go/no-go 지점이었다 — 판정: 조건부 통과(2026-07-27).**

- **통과**: 로그인덱스 조인 전제 성립(91.6%). LLM 단계로 진행 가능.
- **재설계 발생**: 통짜 주입 가정이 실측에서 깨져(258,595자 vs 입력 예산 약 133k 토큰) § 발췌로 전환했다(§4). 즉 Phase 2의 산출물 범위가 늘어났다 — 문서 선택까지가 아니라 § 발췌까지다.

**측정을 구현 전에 한 것이 값을 했다**: Phase 0~2를 다 만든 뒤에 통짜 주입이 예산을 넘는 것을 알게 됐다면 Stage 2를 재작성해야 했다. 프로브 스크립트 하나로 착수 전에 드러났다.

**§ 발췌 구현체는 `TentativeDefectTriage/material/excerpt.py`로 이미 작성했다** — 별도 측정 코드가 아니라 Phase 2 의 실제 부품이다(중복 구현 회피). 디렉토리 이름이 정해지면(Phase 0) 파이프라인 쪽으로 옮긴다.

프로브로 확인된 사실:

- `match_key` 최소 길이가 1이고 `:` · `.` · `%s` 같은 키가 존재한다(rheal 532개 중 46개가 길이 8 미만) — 필터 없이 매칭하면 매칭률이 무의미하게 100%에 가까워진다. 프로브는 `--min-key-len`(기본 8)으로 걸러내고 제외 개수를 함께 보고한다.
- 동일 `match_key`가 복수 `file:line`을 가리키는 경우가 **실측 31.2%** — 매칭되어도 위치가 하나로 특정되지 않는다. `ExpertReport.evidence.candidates`로 스키마에 반영(§5).
- **문서 통짜 주입 상한: rheam 258,770자**(13개) / rheal 약 188k자. subsystem 10종이 관측돼 02~09 대부분이 걸리므로 실제 주입량이 상한 근처가 된다. → 통짜 주입 폐기.

**프로브 확장 필요(미구현)**: 현재 프로브는 통짜 주입 **상한**만 재고, § 발췌 후 실제 크기는 재지 않는다. 발췌가 예산 안에 들어오는지 확인하려면 `file:line` 조인 기반 § 추출을 프로브에 추가해 축소율을 측정해야 한다 — Phase 2 잔여 체크리스트의 전제다.

### Phase 3 — Stage 2 LLM 호출

산출물: 공통 질문 Q1~Q7 프롬프트, 관측(A군)/가설(B·C군) 2단계 호출, `ExpertReport` JSON 출력.

확인 체크리스트:

- [ ] **1단계 vs 2단계 실측 비교** (§4 미검증 가정) — 같은 입력으로 나란히 돌려 품질·비용을 대조
- [ ] 산출물이 §5 스키마를 실제로 채우는가(필드 누락 없이)
- [ ] `counter_points`가 형식적으로 채워지지 않는가 — 비었거나 무의미하면 프롬프트를 고칠 신호
- [ ] `build_assumption`이 참조 문서에서 올바르게 발췌되는가
- [ ] 근거로 제시된 `file:line`이 실제로 존재하는가(환각 검사)

### Phase 4 — Stage 3 조립 + 다중 전문가 병렬

산출물: 지정된 전문가 병렬 실행, `ExpertReport` 나열 제시 (§3).

확인 체크리스트:

- [ ] **두 전문가가 실제로 서로 다른 관점을 내는가** — 같은 내용만 반복하면 다중 전문가 구조의 의미가 없다. 이 설계의 핵심 가치를 직접 검증하는 항목
- [ ] 전문가 1명 지정 시에도 동일 경로로 동작하는가
- [ ] 한 전문가의 실패가 다른 전문가 결과를 죽이지 않는가(독립성)

### Phase 5 — 사용자 인터페이스 (추정)

**§10 미해결 사항에 의존**한다 — "기존 소스 수정 금지" 제약과 "사용자가 전문가를 지정하고 결과를 열람"해야 한다는 요구가 충돌한다. 기존 `frontend`를 고칠 수 없으므로 별도 UI, CLI, 또는 다른 방식이 필요하다. 방식이 정해지지 않아 이 Phase의 산출물·체크리스트는 아직 쓸 수 없다.

### Phase 순서에 대한 메모

Phase 3의 프롬프트 품질 개선은 한 번에 끝나지 않고 Phase 4 이후에도 반복될 것이다 **(추정)** — "품질 좋은 분석 결과"가 목표이므로 프롬프트 반복 개선이 실제 작업량의 상당 부분을 차지할 가능성이 높다. Phase 3을 "완료"로 못 박기보다 Phase 4로 넘어간 뒤에도 되돌아오는 것을 전제하는 편이 현실적이다.

### 미해결 질문

- **`format` 열 재대조로 모호성 해소** — 레시피 §2-2 가 "후보가 여럿이면 `format` 열 전체로 재대조"를 규정하는데 구현에 없다. 효과를 측정해보니 rheam FRC 모호 키 68개 중 **14개(21%)만 완전 해소**되고 나머지 54개는 `format` 이 동일하다(같은 로그문이 여러 호출부에 존재). 싸므로 넣을 가치는 있으나 31.2% 를 크게 줄이지 못한다 — 남는 모호성은 단일 라인으로 환원 불가이므로 시퀀스 맥락(Q1)으로 좁히고 `candidates`(§5)로 노출하는 현재 방향을 유지한다.
- **`_fact_extract.txt`(25k자) 편입 여부** — DP README 가 소비 대상으로 등재했고 GATE 패턴이 Q2·Q5 에 유용하나, DP 에만 있어 FRC 와 비대칭이다(§4).
- **사내 서버에서 자료 저장소를 pull 할 수 있는지** — 접근 방식 자체는 확정됐다(설정에 `material_root` 지정, §4). LogAA 를 `git pull` 로 갱신한다면 같은 자격증명으로 `SamsungDTV_Analysis` 도 가능하다. 안 되면 자료를 사람이 서버로 옮기고 경로만 맞추면 되므로, 어느 쪽이든 진행은 막히지 않는다.
- **사용자 인터페이스** — "기존 소스 수정 금지"(§2) 제약과 "사용자가 전문가를 지정하고 결과를 열람"해야 한다는 요구가 충돌한다. 기존 `frontend`를 고칠 수 없으므로 별도 UI / CLI / 다른 방식 중 선택이 필요하다. Phase 5가 여기에 막혀 있다.
- Stage 2 프롬프트의 세부 문구·출력 파싱 — 구조와 질문 세트는 확정됐으나(§4), 실제 프롬프트 문장과 JSON 스키마 강제 방식은 구현 시점에 정한다.
