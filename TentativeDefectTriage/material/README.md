# probe — 설계 가정 실측 도구

신규 문제 분석 파이프라인을 **구현하기 전에** 설계 가정이 실제 로그에서 성립하는지 재는 도구. 설계 문서 [§9 Phase 2](../신규%20문제%20분석%20파이프라인%20설계.md)의 go/no-go 판단 근거를 만든다.

파이프라인 코드가 아니다 — 측정이 끝나면 역할이 끝난다. 그래서 아직 이름이 정해지지 않은 신규 코드베이스 디렉토리가 아니라, 검증 대상인 설계 문서 옆에 둔다.

## 왜 구현 전에 재는가

Stage 2 의 핵심 전제는 "로그 라인을 `11_log_index.tsv` 의 `match_key` 에 리터럴 매칭해 코드 위치(`file:line`)와 `subsystem` 을 얻을 수 있다"는 것이다. 이 전제가 무너지면 Stage 2 를 다시 설계해야 한다. Phase 0~2 를 다 만든 뒤에 알게 되는 것보다, 스크립트 하나로 미리 아는 것이 훨씬 싸다.

부수적으로 §4 의 두 번째 가정("문서가 짧아 통짜 주입 가능")도 같이 측정한다.

## 진행 방식 (사내 로그를 밖으로 내보내지 않는 흐름)

실제 defect 로그는 사내에만 있으므로 측정과 분석을 분리한다:

1. 스크립트를 사내 환경에 확보한다
2. **사내에서** 실제 로그로 스크립트를 돌려 결과 마크다운을 만든다
3. **결과 수치를 전달한다** — 리포트의 표 값을 읽어 옮기면 된다
4. 결과를 근거로 Phase 2 go/no-go 를 판단하고 설계 문서 §9·§10 을 갱신한다

3번이 파일 커밋·푸시가 아닌 이유: 사내 환경에서 이 저장소로 결과 파일을 올릴 수 없는 것으로 확인됐다(2026-07-27). 대신 수치를 옮겨 적는 방식으로 진행한다 — 기본 설정(`--samples 0`)에서 **리포트의 수치·분포에는 로그 원문이 포함되지 않으므로** 옮겨 적는 데 문제가 없다. 아래 "사내 로그 취급" 참고.

전달할 항목(리포트에서 바로 보이는 값):

- 대상: 모듈(FRC/DP) + 칩
- 매칭률: **모집단 기준** 비율 (전체 기준과 구분해서)
- 모호성 2종: 한 라인에 복수 키 매칭 / 매칭 키가 복수 `file:line`
- subsystem 종류 수
- 컨텍스트 크기: 후보 문서 전체 자수
- 모집단 내 미매칭 건수
- 너무 짧아 제외된 키 개수

## 사용법

```sh
# FRC (드라이버 태그 [S_F])
./probe_match_rate.py \
    --log      /path/to/dmesg.txt \
    --index    /path/to/DTV_soc_driver/analysis/sdp_frc/rheal/11_log_index.tsv \
    --docs-dir /path/to/DTV_soc_driver/analysis/sdp_frc/rheal \
    --driver-tag '\[S_F\]' \
    --out      results/frc_rheal_<날짜>.md

# DP (dmesg 접두는 [DRM-DP], oscarp 만 [DRM-DP:I] → 여는 괄호까지만 잡는다)
./probe_match_rate.py \
    --log      /path/to/dmesg.txt \
    --index    /path/to/DTV_soc_driver/analysis/sdp_drm-dp/rheal/11_log_index.tsv \
    --docs-dir /path/to/DTV_soc_driver/analysis/sdp_drm-dp/rheal \
    --driver-tag '\[DRM-DP' \
    --out      results/dp_rheal_<날짜>.md
```

**칩을 반드시 맞출 것.** 칩마다 `file:line` 과 일부 시그니처가 다르므로(`analysis/sdp_frc/README.md` §4-5), 로그를 뽑은 기기의 칩과 인덱스의 칩이 어긋나면 측정이 무의미하다.

가능하면 **여러 로그로 반복 측정**하는 편이 좋다. 한 건은 그 흐름(부팅/채널전환/대기복귀 등)에 편향돼 있어, 매칭률이 흐름에 따라 크게 흔들리는지 자체가 정보다.

주요 옵션:

| 옵션 | 의미 |
| --- | --- |
| `--driver-tag` | 드라이버 로그를 식별하는 정규식. **생략하면 모집단 기준 비율을 못 낸다** — 사실상 필수. FRC `'\[S_F\]'`, DP `'\[DRM-DP'` |
| `--exclude-level` | 매칭에서 제외할 `level` 값(기본 `T2D`) — 아래 참고 |
| `--min-key-len` | `match_key` 최소 길이 (기본 8). 짧은 키는 오탐원이라 제외한다 |
| `--samples N` | 미매칭 라인 원문을 N건 리포트에 포함 (기본 0 = 미출력) |
| `--out` | 결과 마크다운 경로 (생략 시 stdout) |

## 사내 로그 취급

- 기본값은 **미매칭 라인 원문을 출력하지 않는다**(`--samples 0`). 매칭률·분포 수치에는 로그 원문이 포함되지 않는다.
- `--samples N` 을 쓰면 원문 일부가 리포트에 들어간다. **커밋·푸시 전에 반드시 내용을 확인할 것.**
- 리포트에는 `--log` 로 넘긴 **경로 문자열**이 기록된다. 경로 자체가 민감하면 파일을 임시 위치로 복사해 돌리거나 결과에서 지운다.

## `--exclude-level T2D` 를 왜 기본으로 두는가

`analysis/sdp_drm-dp/README.md` §4.6: **`level` 열이 `T2D` 인 행은 dmesg 기대 로그로 세면 안 된다.** 전부 `#ifdef CONFIG_T2D_DEBUGD` 안이라 커널 설정에 따라 컴파일 자체가 빠지고, `PRINT_T2D` 의 실제 정의도 이 저장소 밖(커널 `t2ddebugd`)이라 출력 경로가 미확인이다.

규모가 작지 않다 — **FRC rheam 904행 중 362행(40%)**, DP rheam 1,791행 중 216행. 특히 FRC 의 `debug_t2d` subsystem 은 377행으로 **인덱스 최대 규모**라, 제외하지 않으면 subsystem 분포가 실제 dmesg 와 무관하게 왜곡되고 발췌 대상 문서도 잘못 넓어진다.

## `--min-key-len` 을 왜 두는가

`11_log_index.tsv` 의 `match_key` 는 포맷 문자열에서 변수부(`%s`/`%d`/`%x`)를 떼어낸 리터럴 조각이다. 그런데 고정부가 거의 없는 포맷도 있어서, rheal 인덱스 532개 키 중 최소 길이가 **1** 이고 `:` · `.` · `%s` 같은 키가 실제로 존재한다. 이런 키를 그대로 쓰면 거의 모든 라인에 걸려 매칭률이 무의미하게 100% 에 가까워진다.

기본값 8 은 중앙값(21) 대비 보수적인 하한이다. 제외된 키 개수는 리포트에 함께 집계되므로, "특정 불가한 로그가 얼마나 되는가"를 매칭률과 같이 읽을 수 있다.

## 결과를 어떻게 읽는가

**모집단 기준 매칭률**(드라이버 태그를 가진 라인 중 매칭된 비율)이 핵심 지표다. 전체 라인 기준 비율은 무관한 커널 로그가 분모에 섞여 낮게 나오는 것이 정상이다.

해석 기준은 사후 합리화를 막기 위해 **측정 전에** 리포트 템플릿에 박아 두었다(스크립트가 자동 출력). 경험적 근거가 없는 추정값이며 실측 후 조정될 수 있다.

같이 볼 것:

- **모호성 비율** — 매칭됐어도 위치가 하나로 특정되지 않는 경우(동일 포맷이 여러 곳에 존재). rheal 인덱스에는 그런 키가 49개 있다. 비율이 높으면 Stage 2 가 위치를 단정하지 않도록 설계를 보강해야 한다.
- **subsystem 종류 수 + 컨텍스트 크기** — 로그가 여러 서브시스템에 걸치면 선택 문서가 늘어난다. 참고로 rheal 문서 전체는 약 188k 자이므로, 상한에 가까워지면 §4 의 통짜 주입 가정을 재검토해야 한다.

## 검증 상태

- **동작 확인** — 합성 로그(실제 인덱스에서 `match_key` 를 추출해 `[S_F]` 태그를 붙인 12줄 + 무관 커널 라인 20줄 + 미지의 드라이버 라인 3줄)로 확인. 모집단 15줄 중 12줄 매칭(80%), 무관 라인은 모집단에서 정상 제외됨.
- **실측 완료(2026-07-27, FRC/rheam)** — 사내 실제 로그로 측정. 결과와 그에 따른 설계 변경은 설계 문서 §4 "Stage 2 실측 결과" 참고. 요약: 모집단 기준 매칭률 **91.6%**(전제 통과), 위치 모호성 **31.2%**(스키마 수정), 통짜 주입 상한 **258,595자**(예산 초과 → § 발췌로 전환).

## `excerpt.py` — § 발췌 추출기

**이건 측정 전용 도구가 아니라 Stage 2 의 실제 부품이다.** 지금은 CLI 로 발췌 크기를 재는 데 쓰고, Phase 2 에서 파이프라인이 같은 모듈을 호출한다 — 같은 로직을 두 번 만들지 않기 위해서다. 신규 코드베이스 디렉토리가 정해지면(Phase 0) 그쪽으로 옮긴다.

관측된 `file:line` 과 겹치는 `##`/`###` 섹션만 뽑는다. 인용 형식은 실제 문서를 집계해 대응했다 — 전체경로(1,090건) · **범위 `:1709-1712`(543건)** · 파일명만(51건) · 축약형 `(:1609)`(27건, 직전 파일 문맥으로 귀속).

```sh
# 로그에서 관측 집합을 직접 도출 (사내에서 이대로 실행)
./excerpt.py --log dmesg.txt \
             --index /path/analysis/sdp_frc/rheam/11_log_index.tsv \
             --docs-dir /path/analysis/sdp_frc/rheam \
             --driver-tag '\[S_F\]' --out excerpt_report.md

# 발췌 본문까지 저장 (프롬프트 주입 형태 확인용)
./excerpt.py ... --dump-excerpt excerpt_body.md
```

### 측정 결과 (2026-07-27, rheam)

**관측 집합은 실제 로그가 아니라 인덱스 기반 합성**(T2D 제외 후 상위 10 subsystem 의 20% 샘플 77개)이라 **지표로만 읽을 것**. `--log` 로 실제 로그 재측정이 필요하다.

| window | 축소율 | 실제 주입량 | 발췌 § |
| --- | --- | --- | --- |
| 0 | 3.1배 | 84,405자 | 37 / 226 |
| **10 (기본값)** | **2.2배** | **117,816자** | 62 / 226 |
| 40 | 1.8배 | 145,787자 | 86 / 226 |

- **"약 10배" 추정은 틀렸다** — 최선이 3.1배다. 축소율이 **관측 집합 크기에 둔감**하다는 것이 두 번 확인됐다(748→149개: 1.6→1.8배 / T2D 제외로 149→77개: 2.1→2.2배). § 단위가 인용 분포에 비해 거친 것이 구조적 원인이므로, **더 줄여야 하면 window 조정이 아니라 발췌 단위를 잘게 하거나 임베딩 chunk 검색을 검토해야 한다.**
- 그래도 예산 안에는 든다(입력 여유 약 133k 토큰 대비 117,816자 ≈ 59~79k 토큰).
- 통짜 유지 문서(10·11)는 11,694자뿐이라 바닥 제약이 아니다. fallback 파일 1종·미인용 관측 파일 0종으로 **정밀도는 양호**.
- window 기본값은 40→10 으로 낮췄다. 0 이 가장 작지만 문서와 로그인덱스가 각각 생성돼 라인이 어긋날 수 있어(stale 문제), 드리프트를 흡수하면서 예산에도 드는 10 을 택했다.
