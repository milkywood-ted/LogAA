# MCP 기반 동적 지식 조회

## 개요

분석 프로파일에 MCP 서버와 검색 용어를 매핑해두고, 해당 용어가 로그 또는 매칭 케이스에 실제로 등장했을 때만 MCP 서버를 조회하여 컨텍스트를 보강하는 방식.

---

## 설계 방향

### 지식 계층 구조

```
사전지식 (SQLite)       → 압축된 도메인 요약 (항상 주입, 소량)
ChromaDB 케이스         → 유사 사례의 핵심 용어 추출
      ↓
  MCP 서버 조회          → 추출된 용어로 검색 → 관련 문서 스니펫
      ↓
  Stage 5 LLM 컨텍스트에 추가 주입
```

### 프로파일 JSON 구조 (예시)

```json
{
  "name": "ATA 스토리지",
  "knowledge_refs": ["ATA 디바이스 특성"],
  "mcp_lookups": [
    {
      "terms": ["NCQ", "SATA", "ATA"],
      "server": "confluence",
      "space": "STORAGE"
    },
    {
      "terms": ["firmware", "RVT"],
      "server": "confluence",
      "space": "FIRMWARE-DB"
    }
  ]
}
```

### 파이프라인 흐름

```
Stage 1 정제 로그 + Stage 2 매칭 케이스
    ↓
로그/케이스에서 mcp_lookups의 terms 등장 여부 확인
    ↓ (등장한 terms만 선별)
해당 MCP 서버 조회 → 스니펫 수집 (페이지당 토큰 상한 적용)
    ↓
Stage 5 컨텍스트에 주입
```

---

## 주요 설계 결정 사항

### 검색 범위 제한
- 용어 품질에 의존하지 않고 Space/Label을 사전에 지정하여 노이즈 제어
- 도메인 전문가(프로파일 작성자)가 범위를 좁혀주는 역할 담당

### 조건부 조회
- 용어가 로그에 실제로 등장했을 때만 MCP 호출
- 불필요한 네트워크 비용 및 토큰 증가 방지

### 서버 다변화
- `server` 필드로 Confluence 외 Jira, GitHub Wiki 등 다른 MCP 서버 확장 가능
- 동일 구조로 여러 서버 동시 조회 지원

### 토큰/속도 영향 (추정)
| 항목 | 추가 토큰 | 추가 시간 |
|---|---|---|
| MCP 검색 (네트워크 왕복) | 0 | +1~3초 |
| 스니펫 컨텍스트 주입 | +500~2000 토큰 | +0.5~1초 |

- Stage 5 LLM 호출이 이미 주 병목이므로 체감 영향은 제한적
- 스니펫 길이 상한(예: 페이지당 200토큰) 필수
